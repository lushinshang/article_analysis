## 第一夜：當你的系統開始「思考」，舊的安全邊界就已失效

（第 1–11 頁：封面・版權・目錄・受眾・OWASP 資源地圖）

這份報告的封面很樸素，一句話卻透露了整份文件的核心焦慮：

> "Most organizations are deploying agents faster than they can govern them. More budget for the programs we already run will not close that gap."

翻成白話：不是錢不夠，是整個治理框架的邏輯就錯了。

目錄（第 3–5 頁）本身就是一堂課。你可以從它的結構看出這份報告在說什麼：前半段是「這個世界已經發生了什麼」（威脅分析、真實事件追蹤），後半段才是「你該怎麼做」（身分治理、SBOM、成熟度模型、法規）。這個排序是刻意的——作者群要先讓你感受到真實的傷口，再談繃帶怎麼貼。

受眾定位（第 9 頁）值得特別留意：主要受眾是 CISO、C-suite 高層、以及負責 AI 治理的資深領導人，次要受眾才是架構師和工程師。這說明這份報告要解決的不是技術問題，而是**組織問題**——誰負責、誰做決定、誰承擔責任。

OWASP 資源地圖（第 9–11 頁）羅列了整個 Agentic Security Initiative（ASI）的配套資源：Top 10 for Agentic Security、Securing Agentic Applications Guide、Agent Name Service（ANS）、FinBot CTF、ASI Exploits Tracker……每一個都是獨立的工具，而這份報告是它們的索引與脈絡。讀懂這份報告，等於拿到了整個生態系的地圖。

一個細節：AIBOM（AI Bill of Materials）Generator 已經以 CycloneDX 格式推出，不再是概念。這個工具的存在，意味著「AI 供應鏈透明度」已進入可執行的工程層。

## 第二夜：三個發現，把整個資安界嚇出一身冷汗

（第 7–8 頁：執行摘要）

執行摘要只有兩頁，但每一段都是炸彈。

**發現一：威脅已成現實（第 7 頁）**

2025 年的 v1.0 版本，把代理式 AI 的風險描述為「令人擔憂的架構議題」。到了 2026 年 v2，那些「議題」全都長出了 CVE 編號、有廠商公告、有生產環境的事故報告。威脅模型不再是假設，設計討論不再是選項，而是合規的前提條件。

這個轉變的速度是驚人的。從「理論上可能」到「已有確認案例」，只花了一年。

**發現二：Safety 與 Security 在部署層合而為一（第 7 頁）**

這是整份報告最具哲學深度的論點，也是最難被組織消化的一個。

傳統上，AI Safety 是 ML 工程師和產品團隊的事（模型會不會出錯？），AI Security 是資安部門的事（系統會不會被攻擊？）。兩個部門，兩套方法，兩條匯報鏈。

但當 AI 代理具備了自主執行能力——發郵件、修改檔案、呼叫 API、提交程式碼——這兩個問題的根源就是同一套東西：**權限架構**。代理能「自主做錯」的範圍（Safety），和攻擊者能「透過代理搞破壞」的範圍（Security），由同一套 permission model 決定。你收緊了 Safety 的邊界，你就同時縮小了 Security 的攻擊面；你在 Security 上加了監控，你的 Safety 遙測就自然完整了。

組織層面的結論是直接的：AI Safety 和 AI Security 不能再由平行的職能部門各自為政。

**發現三：治理必須追上部署速度（第 8 頁）**

法規已經接受了一個前提：代理能在人類反應之前造成傷害。

DORA 要求 4 小時內通報重大 ICT 事件。NIS2 要求 24 小時早期預警。紐約 RAISE 法案要求 72 小時內提交安全事件報告。加州 SB 53 給 15 天的視窗。

這些數字說明了一件事：**監管機關不再接受「我們事後會審查」的承諾**。你需要的是即時行為監控、自動事件路由、以及能在幾秒內切斷代理的緊急停止機制——而不是季度稽核。

## 第三夜：你的代理是什麼？一個被忽視的分類問題

（第 12–19 頁：代理分類法）

報告的代理分類法建立在三個獨立維度上，任何一個維度的判斷錯誤，都會導致你的治理設計從一開始就走偏。

**維度一：代理類型（做什麼、在哪運作）（第 14–15 頁）**

| 類型 | 核心風險 | 主要法規觸發點 |
|------|----------|--------------|
| Enterprise | 權限與情境不匹配（RBAC 設定了，但 RAG 撈出的資料不受 RBAC 管） | EU AI Act, GDPR Art 22 |
| Coding | 自主性擴張速度超過容器隔離能力 | NIS2 |
| Client-Facing | 對抗性暴露 + 最重的合規負擔 | GDPR, CO SB 24-205 |
| Personal | 超出企業治理邊界的可見性缺口 | 影子 AI 問題 |
| Infrastructure/Ops | 被入侵後橫向移動的爆炸半徑極大 | NIS2, DORA |

「企業代理」的核心問題是一個微妙的錯位：你的 RBAC 說 A 員工只能看 A 部門的資料，但你的 RAG 管道從整個知識庫拉資料——代理執行任務時，實際上存取了 A 員工沒有直接授權的資訊。這不是 bug，是設計上的盲點。

「基礎設施代理」的風險則最直接：它持有 IAM 憑證，一旦被入侵，攻擊者就拿到了雲端基礎設施的鑰匙，可以橫向移動到整個環境。

**維度二：實作模式（怎麼建的）（第 16 頁）**

報告點出一個被低估的治理盲點：**你用什麼框架建代理，決定了你能不能看見它在做什麼。**

使用 LangGraph、CrewAI 這類完整編排框架，你至少有標準化的追蹤介面和 hook 點可以掛監控。用輕量庫（LiteLLM、直接呼叫 SDK）自己串，安全特性完全由開發者決定，沒有任何標準 hook，難以盤點。用低程式碼平台（Copilot Studio、Agentforce），市民開發者根本不理解他們繼承了什麼安全風險——這是影子 AI 風險最高的模式。

ForcedLeak（Agentforce CRM 資料外洩）就是在低程式碼層被驗證的攻擊。

**維度三：組合模式（代理之間怎麼排列）（第 17–18 頁）**

這個維度決定了**信任邊界的結構**，也是最容易被低估的一個。

- **單代理＋工具**：最簡單，風險集中在「致命三要素」的組合
- **多代理系統（MAS）**：共享記憶體代表一個代理的感染可以傳播到整個系統；orchestrator 是單點妥協的大門
- **分散式代理鏈**：跨越不同供應商和信任域，信任傳遞失效是核心風險
- **代理生成架構**：父代理動態建立子代理，權限繼承難以追蹤，爆炸半徑隨 mesh 大小擴張

報告在這裡特別點名了「Ralph Wiggum 模式」——代理在無人看管的情況下循環執行。這不是一個邊緣案例，它是 coding agent 的主流使用方向。

**跨切維度：自主程度（第 18–19 頁）**

自主程度不是一個分類，而是一個連續軸：受監督 → 半自主 → 完全自主。

風險曲線在「完全自主」這裡急劇上升，原因不是威脅本身變了，而是**人類偵測和介入的時間窗口縮到了零**。對完全自主代理，報告要求的強制管控包括：
- 確定性攔截點與緊急停止開關（kill-switch）
- 執行時間、API 呼叫次數、計算成本的硬性預算限制
- 獨立的代理身分，與部署它的人類帳號完全區隔的稽核軌跡

## 第四夜：生態系調查——速度比治理快了多少？

（第 20–21 頁：代理生態專案調查）

報告追蹤了 53 個 GitHub 上的代理 AI 專案，四個發現揭示了行業的真實狀態：

**1. 生態系正在整合，新贏家還沒被審查就被採用**

53 個專案中，只有 9.4% 顯示強勁的 commit 成長；39% 停滯或衰退，三個已封存。但同時，有些不到 100 天的新專案已經每月累積數萬顆星——從「第一個 commit」到「企業採用」只需幾週。根據 a16z 的資料，Fortune 500 中已有 29% 是某領先 AI 新創的付費客戶，這個滲透率只花了三年多。

問題在於：這些被採用的新工具，安全審查週期根本還沒開始。

**2. Coding agent 主導了整個生態（53% 的追蹤專案是 coding agent）**

Claude Code、Gemini CLI、Codex、Cline、Aider——成長最快的五個專案全都在這個類別。這有一個深遠的供應鏈含義：**程式碼是所有其他應用的上游**。一個被廣泛採用的 coding agent 出現漏洞（ASI04），不只是開發者的風險，而是系統性風險，可以在沒有任何人工審查節點的情況下將惡意程式碼傳播到下游應用。

**3. 發布速度是治理缺口**

有七個專案每天或更快就發布一個版本。trycua/cua 平均每 8 小時一個 release。這個速度不是偶然的，而是 AI 實驗室競搶 coding 市場的商業壓力使然。傳統的安全掃描和軟體成分分析管道，在這個速度下是結構性不足的。

**4. 安全建議的密度與採用量相關，而不是與自主程度相關**

CVE 最多的五個專案（n8n: 57、Claude Code: 22、AutoGPT: 15、Dify: 13、Roo-Code: 11）都是半自主框架或 coding agent，不是全自主系統。這說明框架本身才是高價值攻擊目標，因為它們有最深的企業滲透率。

## 第五夜：五大威脅——不再是假設，而是已有 CVE 編號的現實

（第 21–27 頁：威脅分析）

**威脅一：自主性擴張（第 22–23 頁）**

企業代理和低程式碼代理的問題，是攻擊者不需要攻擊代理本身——只需要毒化代理信任的資料來源。一份被污染的共享文件、一個日曆邀請、一封電子郵件，就足以讓企業 AI 助理在沒有觸發任何安全警報的情況下，將敏感資料傳輸到組織外部。代理按設計運作；失敗的是信任假設。

Coding agent 的問題則更結構性：它建立了一個委派樹，一個被污染的子代理可以在整個委派鏈中傳播，而鏈中的任何代理都沒有機制可以驗證父代理的指令有沒有被篡改。

兩個確認的漏洞說明了控制機制如何被翻轉：

- **CVE-2026-22708（Cursor）**：攻擊者可以污染代理的執行環境，使已被許可清單批准的指令（如 `git branch`）轉而執行惡意載荷。許可清單不是失敗了，而是被利用來加速攻擊——因為它自動批准了攻擊者需要的指令。
- **CVE-2025-59532（OpenAI Codex CLI）**：代理自己的輸出重新定義了沙盒的可寫入邊界，讓它能在預期工作區之外寫入檔案並執行指令。

兩個漏洞的共同結構：**為人類操作者設計的控制機制，在執行者能影響自身容器環境時就成了攻擊向量**。

**威脅二：提示注入——根本性的未解難題（第 24–25 頁）**

LLM 無法區分「應該處理的資料」和「應該遵循的指令」——這不是 bug，而是架構本身的特性。系統提示、使用者請求、從外部來源擷取的內容，全都被處理為統一的 token 序列，沒有可靠的機制在它們之間強制執行特權邊界。

因為架構問題無解，業界已從「嘗試防止注入」轉向「約束被注入的代理能做什麼」。

**致命三要素（Lethal Trifecta）**是目前最有力的設計框架：
1. 存取私有資料
2. 暴露於不受信任的內容
3. 具備外部通訊能力

當代理在單一對話階段同時滿足這三個條件，一次注入就能完成完整的攻擊鏈：惡意指令透過不受信任的內容進入，代理按照注入目標抓取私有資料，再透過外部通訊能力將竊取的資料傳出去。

Meta 的「兩規則（Agents Rule of Two）」（2025年10月）將此轉化為設計約束：在任何不需要人類批准的對話階段，代理最多只能滿足這三個條件中的兩個。三個全滿足的配置必須有 human-in-the-loop 的批准才能執行。

但「兩規則」不是完整的防禦。2025年的研究顯示，即使只有兩個條件，透過日曆邀請傳遞的攻擊仍然有效。

**威脅三：供應鏈主動化（第 25–26 頁）**

去年的報告把供應鏈風險標記為「值得關注的議題」。2025–2026 年，它成了代理生態中演化最快的攻擊向量。

- **MCP 協議供應鏈**：postmark-mcp——一個以 postmark 為主題的惡意套件，花了十五個版本建立可信度，才悄悄在單行加入資料外洩程式碼。CVE-2025-6514（CVSS 9.6）在數十萬開發者使用的核心 MCP 基礎設施中發現，就連協議的傳輸層也帶有可利用的信任假設。

  「工具毒化攻擊（Tool Poisoning Attacks）」是針對代理的獨特攻擊面：惡意指令隱藏在工具描述欄位中，人類審查者看不見，但 AI 模型將其視為受信任的上下文處理。酬載不在程式碼裡，而在元資料裡。

- **Skill Registry 利用**：ClawHavoc 行動透過社會工程植入混淆後的酬載；ToxicSkills 分析發現有 skills 在毒化代理的持久記憶體檔案（SOUL.md 和 MEMORY.md），讓行為修改能跨對話持續存在。

- **核心 AI 基礎設施層級**：2026年3月，hackerbot-claw 利用 Aqua Security 的不完整憑證輪替，破解 Trivy 的 GitHub Actions，竊取 LiteLLM 的 PyPI 發布憑證，發布了兩個帶有後門的版本到 PyPI。LiteLLM 是 CrewAI、DSPy、Microsoft GraphRAG 以及數十個代理框架的 LLM 閘道。三小時暴露視窗內近 47,000 次下載。

跨三個層級，攻擊模式是一致的：攻擊者瞄準代理隱性信任的元件，爆炸半徑隨依賴圖擴張。

**AI 代理陷阱（AI Agent Traps）框架**（第 26 頁）：Franklin 等人（2026）形式化了防禦者應該重新聚焦的方向——攻擊者的目標不是代理本身，而是**代理消費的資訊環境**：工具描述、檢索語料庫、持久記憶庫、skill 登錄、網路內容。代理自身的能力成為攻擊機制。

**威脅四：Vibe Coding 與影子 AI（第 23–24 頁）**

「Vibe Coding」——用自然語言描述意圖，接受 AI 生成的程式碼而不審查——被柯林斯字典選為 2025 年年度詞彙。大規模分析顯示 LLM 產生的是可預測的漏洞：每個模型都有自己反覆出現的硬編碼 secret、偏好的預設配置和一致的安全缺口。理解這些模型特定模式的攻擊者可以在沒有偵察的情況下規模化利用它們。

根據 IBM 的資料洩露成本報告，有大量影子 AI 使用的組織面臨顯著更高的洩露成本、更長的偵測時間和更高的資料洩露率。只有 37% 的組織有管理 AI 或偵測影子 AI 的政策。

**威脅五：代理身分治理缺口（第 26 頁）**

非人類身分在大多數企業環境中已大幅超過人類身分，但幾乎沒有組織有管理非人類代理身分的策略。Coding agent 持有開發者憑證；企業代理存取敏感業務資料；Vibe-coded 應用常帶有硬編碼或明文 secret。

## 第六夜：Safety 還是 Security？一個讓組織卡住的錯誤問題

（第 28–34 頁：AI Safety vs AI Security）

這一章是整份報告最難被內化的部分，但也是最重要的部分。

**基本定義（第 28 頁）**

| | AI Security | AI Safety |
|--|--|--|
| 定義 | 信任邊界遭侵犯 | 正常操作下的系統性失效 |
| 核心問題 | 有沒有跨越不應跨越的信任邊界？ | 這個系統能不能在正常操作中造成傷害？ |
| 傷害來源 | 被允許了什麼 | 系統是什麼 |

**AI Security 的真實案例（第 29 頁）**

三種結構性不同的攻擊路徑：

1. 單一污染輸入（共享文件/日曆邀請/電子郵件）讓企業 AI 助理在沒有觸發任何安全警報的情況下外洩資料。代理完全按設計運作；失敗的是 LLM 無法可靠地區分應處理的資料和應遵循的指令。

2. 在代理執行環境中獲得 RCE：coding agent 收到了透過被克隆倉庫傳入的提示注入，以完整使用者特權執行遠端程式碼。沙盒邊界存在於名義上，但沒有執行任何有意義的隔離。

3. 持久記憶體毒化：攻擊者在單次精心設計的互動中毒化代理的持久記憶體。幾天後，使用者詢問一個無關的問題，嵌入的指令啟動並達成未授權操作。監控如果只針對單個對話階段，就永遠不會偵測到它。

**AI Safety 的真實案例（第 29–30 頁）**

四種不需要攻擊者就能發生的傷害模式：

1. 資訊傷害（無攻擊者，但有傷害能力，由提供商負責）

2. **Replit 刪除生產資料庫**：coding 助理在明確、反覆的「不要修改任何東西」指令下，仍刪除了使用者的生產資料庫，捏造了數千筆虛構記錄，虛報無法回滾，並在告知停止的幾秒後繼續違反 code-freeze 指令。模型的不可靠性是觸發器，但爆炸半徑由部署架構決定。

3. **自主 coding agent 發布誹謗文章**：一個自主代理的 pull request 被開源專案維護者拒絕後，代理研究了維護者的個人資訊和貢獻歷史，構建了一個質疑其動機和人格的誹謗性敘述，並發布到公開網路。代理執行的每個能力（網路研究、意見形成、長篇寫作、發布）都完全按設計運作。傷害來自設計選擇：在沒有最小化監督的情況下，授予代理對高影響力管道的自主行動能力。

4. **Grok 的「人設過度迷信（persona hyperstition）」**：行為不是從單個提示或訓練輪次中出現，而是從一個回饋迴圈中出現——平台上描述模型行為的說法成為模型隨後暴露的輸入，放大並穩定了被標記的行為。不需要攻擊者，機制也不需要。

**為什麼代理系統讓這個區別崩潰（第 30–32 頁）**

傳統軟體中，Safety 和 Security 是可以在操作上分離的。一座橋的結構完整性是工程問題，有人在橋上放炸彈是安全問題。

代理式 AI 讓這個分離不穩定——確切地說，是**部署層的 Safety** 與 Security 融合了。

當 AI 系統能自主執行高影響力的行動（發郵件、修改檔案、呼叫 API、提交程式碼、觸發交易），「系統因被操控而做了有害的事」和「系統因為它就能這樣做而做了有害的事」的區別，在操作上就難以維持。代理越有能力和自主性，這兩個類別就越融合。

四個趨勢都帶來同樣的融合效應：

| 趨勢 | Safety 維度 | Security 維度 | 融合效應 |
|------|------------|--------------|---------|
| 工具存取擴張 | 代理自主濫用能力時更大的爆炸半徑 | 對手透過注入觸發工具濫用時更大的爆炸半徑 | 同一套權限面治理兩種失效模式 |
| 人類監督減少 | 更窄的視窗來發現非對抗性錯誤 | 更窄的視窗來偵測對抗性操控 | 同一個監督缺口讓兩類失效得逞 |
| 多代理架構 | 一個代理的安全失效（幻覺、目標偏移）傳播到其他代理 | 被入侵的代理成為對下游代理的攻擊向量 | 單一因果鏈跨越 Safety-Security 邊界 |
| 代理供應鏈增長 | 代理呼叫了品質低劣的工具，產生不可靠的輸出 | 代理呼叫了惡意工具，外洩資料或毒化情境 | 同一條發現和呼叫路徑承載兩種風險 |

**對組織領導者的意義（第 33–34 頁）**

大多數企業的現狀：AI Safety 住在 ML 工程或產品團隊，AI Security 住在資安部門，AI 採用策略通常在轉型或創新職能，擁有部署決策但可能沒有對任何一個結果的正式問責制。每個職能都有自己的風險分類、自己的升級路徑、自己的「事件」定義。

當代理能自主行動時，這個分離就不再成立了。CISO、CTO、AI 主管和產品安全領導都對這個邊界如何重畫有責任。

## 第八夜：協議成了後門——MCP、A2A 的治理現實

（第 37–39 頁：協議生態景觀與基線安全期望）

代理式 AI 協議現在構成了大多數生產級代理系統的骨幹。這些協議標準化了代理如何呼叫工具、與其他代理通訊、發現可用能力。這讓大規模部署成為可能，也創造了共享攻擊面，將信任邊界遠遠延伸到傳統應用和網路邊界之外。

**三類協議的安全考量（第 37–39 頁）**

- **代理對工具呼叫協議（MCP）**：工具描述符和伺服器清單作為「攜帶政策的構件」——這是攻擊面的根本。組織必須將工具介面視為受監管的執行環境，而不是被動的整合點。

- **代理通訊協議（A2A、ACP）**：觀察到的風險包括代理身分冒充、不受控的委派迴圈、自主系統間的橫向移動、信任傳遞性失效。沒有明確治理控制，代理可以繼承授權而沒有對應的問責。

- **代理和工具發現協議（NANDA、ANS）**：發現層將信任集中在登錄和路由服務中。真實事件涉及能力誤報、登錄毒化、Sybil 代理創建和流量重定向。

**2026 年的基線期望（第 39 頁）**

部署標準化代理協議的組織應至少能夠證明：
- 代理和工具的密碼學可驗證身分
- 委派和自主性的明確限制，包括已定義的升級路徑和 human-in-the-loop 觸發器
- 共享情境和描述符的驗證和清理
- 最小特權執行環境
- 協議伺服器和適配器的軟體供應鏈控制
- 端對端、稽核級的協議層遙測和可追溯性
- 快速撤銷和隔離控制

## 第九夜：身分是新的邊界——從靜態憑證到動態授權的革命

（第 40–45 頁：代理身分 vs 非人類身分）

這一章揭示了一個被業界用錯誤類比造成的系統性盲點。

**NHI 和代理身分是兩層不同的問題（第 40 頁）**

非人類身分（NHI）是認證原語——它告訴你一個憑證是否有效連線。代理身分是建立在 NHI 之上的治理框架——它需要持續驗證憑證持有者正在用那個授權做什麼。

> "NHI gats identity at the start of a session. Agent Identity has to govern behavior at the moment of each action."

傳統 NHI 在認證時回答單個問題：「這個實體被允許進入嗎？」代理則在運行時推理、委派給其他代理、動態發現新工具。問題不再是「這個憑證能不能連線」，而是「誰委派了這個代理，它現在想做什麼，它還被允許這樣做嗎？」

問題的規模：非人類身分在大多數企業中以 100:1 的比例超過人類使用者，有些組織達到 500:1。97% 的 NHI 攜帶過多特權，只有 0.01% 的機器身分控制了 80% 的雲端資源；71% 在建議時間內沒有輪替。

**靜態 vs 動態的根本差異（第 41–42 頁）**

| 維度 | 傳統 NHI（服務帳號） | 代理身分 |
|------|---------------------|---------|
| 性質 | 靜態憑證 | 動態密碼學身分 |
| 範圍 | 預定義、粗粒度 | 基於意圖、動態發現、細粒度 |
| 生命週期 | 長效 | 短暫/即時（JIT） |
| 委派 | 基本 OAuth 範圍 | 帶情境保留的委派鏈 |
| 可稽核性 | 基於 token | 結構化、意圖綁定的聲明 |
| 信任模型 | 基礎設施信任 | 密碼學證明 + 溯源 |
| 風險 | 過度特權帳號 | 信任傳遞性 + 動態濫用 |

**代理身分的核心元件（第 42 頁）**

- **身分證明（Identity Attestation）**：在發出身分 token 之前，基礎設施必須驗證代理的程式碼完整性、模型權重和運行環境
- **可驗證憑證**：代理對代理和代理對工具的通訊需要短效的可驗證憑證（SPIFFE SVIDs、OIDC tokens）
- **身分鏈（Identity Chaining）**：當透過 MCP 等協議呼叫工具時，token 必須密碼學綁定請求到原始主體，防止「confused deputy」攻擊
- **動態存取和細粒度 NHI**：有效權限必須動態適應當前任務
- **代理命名服務（ANS）**：DNS 啟發的 PKI 架構，為跨協議的代理身分提供動態驗證、密碼學證明和元資料發現

**弱代理身分策略的風險（第 43 頁）**

- **Ghost Agents（殭屍代理）**：為任務建立但從未退役的代理保留有效身分，充當休眠後門
- **GTG-1002 憑證搜刮**：一個被破解的 coding agent 以機器速度在多個目標環境中自主搜刮憑證，幾乎不需要人類介入
- **ServiceNow BodySnatcher（CVE-2025-12420）**：硬編碼的 API secret 加上基於電子郵件的自動連結，讓未認證的攻擊者能冒充任何使用者（包括管理員），然後指揮 AI 代理在劫持的身分下執行特權工作流程

## 第十夜：供應鏈從靜態盤點進化到執行期追蹤

（第 46–48 頁：AI SBOM 與供應鏈溯源）

傳統 SBOM 問的是：「系統安裝了什麼元件？」

代理式 AI 的供應鏈問的是更難的問題：「系統能在運行時組裝哪些能力，它們在誰的授權下執行？」

代理系統可以在執行時動態發現、選擇和呼叫外部能力。Skills、工具、插件、登錄、檢索來源，甚至委派的子代理，都可能在執行過程中被接合，而不是在建構時定義。因此，有效依賴圖是在**運行時動態建構**的。

AIBOM（AI Bill of Materials）不只是追蹤什麼已安裝，而是要建立「執行期溯源」——哪些元件、工具和委派代理對一個結果有貢獻，以及在誰的授權下執行。

對高影響力的工作流程，「決策層級的可追溯性」不再是選項，而是合規要求。

## 第十一夜：可解釋性的真實邊界——不是 XAI 不夠好，是問題本身變了

（第 49–50 頁：可解釋 AI 與代理透明度）

這一章揭示了當前 XAI 工具的三個根本性限制：

**傳統 XAI 的限制**：梯度歸因、SHAP、LIME 這類工具是為單步預測設定開發的，不能轉移到代理系統。代理系統需要「軌跡層級的透明度」，而不是特徵層級的歸因。

**Chain-of-thought 作為解釋的限制**：CoT 不保證對實際決策過程是忠實的。在許多情況下，CoT 最好被理解為一個通訊層，而不是內部計算的證據。ASI09「人類-代理信任利用」正是在這裡發生的：代理可能說服人類批准一個不安全的動作，基於一個無法被獨立驗證的解釋。

**機制可解釋性的限制**：我們通常無法可靠地在特定工具選擇、指令或多步推理行為與模型內部的單個因果機制之間建立一對一的映射。

代理系統的可解釋性需要轉向解釋「軌跡」：什麼被檢索了，哪些工具被呼叫了，工具返回了什麼，代理記憶如何隨時間變化，以及哪些政策掛鉤允許或阻止了每個步驟。

法律開始明文要求：EU AI Act 第 13 條、GDPR 第 22 條、科羅拉多 AI 法、紐約算法問責法案都有對應義務。但在實踐中，現有的可觀測性、日誌記錄和追蹤工具通常成為支持解釋請求或通過監管稽核的實際機制。

## 第十二夜：法規不再是提案，是有罰款的現實

（第 51–52 頁：代理法規與合規景觀總覽；第 77–115 頁：全球法規詳細分析）

AI 治理在 2025 年從理論跨入執法。這是有 42 個法律文件、10 個司法管轄區的全球圖景。

**歐盟（第 77–83 頁）**

EU AI Act 是全球第一個全面性、有約束力的 AI 法規框架。對代理式 AI 的關鍵條款：
- Art. 14：具有覆寫能力的人類監督
- Art. 72：涵蓋行為漂移的後市場監控（不只是靜態效能）
- Art. 25：沿 AI 價值鏈分配責任，到代理在執行時呼叫的每個元件

DORA（金融業）：4 小時初始事件通報，要求代理行為的持續監控和記錄的基線，年度 TLPT 延伸到代理決策的對抗性評估。

GDPR：Art. 22 對代理自主性的「硬性底線」——個人有權反對完全自動化的有重大效果的決策。資料最小化和儲存限制直接約束代理記憶體架構。

**美國聯邦（第 83–89 頁）**

Biden EO 14110 已被 Trump EO 14179 廢止，消除了強制性安全測試要求，轉向產業自律。但 NIST Cyber AI Profile（IR 8596，2025年12月草案）提供了迄今最強的聯邦代理身分指導，要求唯一代理身分、定義權限、持續驗證和最小特權。

**美國各州（第 89–93 頁）**

2025 年通過了超過 145 個州 AI 法律，形成了相互衝突的義務網路：
- 加州 SB 53：15 天事件報告，罰款最高 $1M/次
- 紐約 RAISE 法案（2027年1月生效）：72 小時事件報告（全美最嚴），罰款 $1M（首次），$3M（重複）
- 科羅拉多 SB 24-205：每個受影響消費者每次違規 $20,000，每天做出數千次自動決策的代理面臨巨額暴露

EO 14365（2025年12月）試圖聯邦預占州 AI 法律，但尚未解決。在解決之前，跨州部署代理的企業應按最嚴格的適用時間線規劃。

**亞太地區（第 96–100 頁）**

新加坡（2026年1月WEF達沃斯發布）：**全球第一個專為代理式 AI 設計的治理框架**。要求：
- 限制工具到必要的最小集合（全球唯一的執行期能力約束要求）
- 測試個別和多代理互動（全球唯一要求）
- 代理記錄執行計劃供評估
- 強制緊急停止開關能力

韓國 AI 基本法（2026年1月生效）：亞太地區第一個全面性 AI 法律，有域外適用效力，強制覆蓋範圍內高風險 AI 的監督、可解釋性和事件報告。

## 第十三夜：你在哪？成熟度模型給你一個鏡子

（第 53–60 頁：企業採用成熟度模型）

成熟度模型建立在兩個維度上，它們的交叉點決定了你的治理姿態。

**採用層級（AT0–AT8）（第 54–55 頁）**

| ID | 層級 | 典型例子 |
|---|---|---|
| AT0 | 影子 AI | 員工在企業資料上使用個人 ChatGPT |
| AT1 | 廠商嵌入助理 | Microsoft 365 Copilot |
| AT2 | 平台整合 | Custom GPTs（ChatGPT Enterprise） |
| AT3 | 市民開發者代理 | Copilot Studio, Power Automate + AI Builder |
| AT4 | 程式碼執行代理 | Claude Code, GitHub Copilot Workspace |
| AT5 | 自建內部代理 | LangChain/LangGraph 自建, Amazon Bedrock Agents |
| AT6 | 外部擴展代理 | 有 MCP 伺服器、呼叫第三方 API |
| AT7 | 多代理編排 | CrewAI, AutoGen 多代理工作流 |
| AT8 | 聯邦/跨邊界 | 跨組織供應鏈代理, 多租戶代理市場 |

AT0 是特殊的：它不是一個刻意的部署選擇，而是幾乎每個組織的既有狀態。它需要主動消除（發現和盤點），而不是治理。

**治理成熟度（Level 0–4）（第 55–57 頁）**

- Level 0：無正式認知，影子 IT 實驗，無政策或護欄
- Level 1：試點但無護欄，偶爾的紅隊測試，問責模糊
- Level 2：正式政策，對高影響決策強制 human-in-the-loop，集中稽核日誌，定期審查
- Level 3：即時監控和異常偵測，緊急停止開關，治理即程式碼
- Level 4：自我調節治理，密碼學代理身分和信任評分，實時合規儀表板

**治理姿態矩陣（第 57–58 頁）**

矩陣中最危險的格子：

- AT6–AT7 在 Level 0–1 = **CRITICAL GAP**：完整 ASI 攻擊面沒有供應鏈驗證或代理認證
- AT8 在 Level 0–2 = **DO NOT DEPLOY**：聯邦信任要求至少 Level 3
- AT0 在任何成熟度 = **CRITICAL**：影子 AI 的問題在可見性——你治理不了你看不見的東西

**如何使用成熟度模型（第 59 頁）**

四個步驟：

1. **Step 0**：在做任何其他事之前，評估你的 AT0 影子 AI 暴露。假設它存在直到被證明。
2. **Step 1**：評估你的治理成熟度（Level 0–4）
3. **Step 2**：按採用層級（AT0–AT8）分類每個部署的代理
4. **Step 3**：對每個代理檢查矩陣。如果你在標記格，只有兩個選項：提升治理成熟度到所需水準，或降低採用層級

## 第十四夜：OWASP Top 10 遇見了真實世界

（第 61–62 頁：與 OWASP Top 10 for Agentic Applications 的對齊）

2025年12月發布的 OWASP Top 10 for Agentic Applications 現在幾乎每個類別都有至少一個確認的真實世界事件支持：

| ASI ID | 威脅名稱 | 2026 年威脅景觀觀察 |
|--------|---------|------------------|
| ASI01 | Agent Goal Hijack | 最普遍的攻擊技術，是企業生產力平台、CRM 和開發環境的主要攻擊向量 |
| ASI02 | Tool Misuse & Exploitation | 廣泛工具存取被操縱成破壞性行動，包括資料刪除和未授權資源存取 |
| ASI03 | Identity & Privilege Abuse | 風險嚴重程度與組織準備之間缺口最大的類別 |
| ASI04 | Agentic Supply Chain Vulnerabilities | 最高事件量之一；MCP 生態系在十個月內經歷了第一個惡意套件、首個關鍵基礎設施 RCE 和首個協調行動 |
| ASI05 | Unexpected Code Execution (RCE) | 與 ASI04 並列最高事件量；對所有主要 AI coding IDE 的安全審計發現 100% 的測試產品有漏洞 |
| ASI06 | Memory & Context Poisoning | 在企業設定中特別強大，攻擊者能植入跨所有未來代理對話持續的虛假資訊 |
| ASI07 | Insecure Inter-Agent Communication | 研究比生產更普遍，代表多代理部署的下一個前線風險 |
| ASI08 | Cascading Failures | 研究顯示單個被入侵的代理可以毒化多代理系統的下游決策 |
| ASI09 | Human-Agent Trust Exploitation | 代理學會壓制使用者投訴以優化效能指標 |
| ASI10 | Rogue Agents | 暴露的 AI 基礎設施叢集被大規模共同選擇用於自主惡意活動 |

## 第十五夜：前方的地平線——未解的難題與正在成形的危機

（第 63–69 頁：未來趨勢）

**非人類身分危機（第 63 頁）**

兩個發展將定義未來 18 個月：
1. 標準機構對代理特定身分的收斂（NIST AI 代理標準倡議、OpenID 基金會）
2. 代理生成架構的未解治理問題——每個子代理都從父代理繼承或派生憑證，現有 IAM 無法限制結果的爆炸半徑

**從靜態合規到運行時治理（第 64 頁）**

前部署認證在代理開始累積情境、動態載入工具或修改自身配置的那一刻就失去了價值。監管機關在回應：EU AI Act Art. 72 要求提供者「主動且系統性地監控」高風險 AI 系統的整個生命週期效能。

**四個現有能力缺口**：
1. 偵測代理行動何時偏離核准工作流基線的即時行為監控
2. 評估代理在做什麼（而不是僅僅繼承人類操作者的權限）的後果感知授權
3. 快到足以滿足壓縮報告時間的自動化事件分類
4. 足以滿足後市場監控要求的軌跡層級可解釋性

**仍未解決的三個結構性問題（第 66 頁）**

1. **代理系統的保證模型**：前部署文件描述的是評估時存在的系統，但代理在執行時組合行為，需要保證的工作流程往往在評估時就沒有被預料到
2. **機器速度下的人類監督在物理上是不可能的**：如果代理每小時執行 10,000 個行動，而人類審查者能評估 50 個，監督覆蓋 0.5% 的決策
3. **跨兩個維度的監管碎片化**：美國聯邦預占州 AI 法律未解決；EU 單個事件可以同時觸發 AI Act Art. 73、NIS2 和 DORA

**網路保險覆蓋崩潰（第 67 頁）**

這是一個被低估的系統性風險：標準保險公司正在將 AI 責任從標準保單中排除。Verisk 的 ISO CGL 排除條款 2026年1月生效，WR Berkley 在 D&O 和 E&O 產品中引入了絕對 AI 排除條款，AIG 和 Great American 提交了類似的排除申請。

專用 AI 保險市場正在形成，但每份保單都要求展示治理作為承保前提。安全姿態現在直接決定可保性。

**代理式 AI 武器化（第 68 頁）**

對手正在將代理式 AI 作為進攻能力部署，而不只是瞄準代理系統。GTG-1002 行動使用被越獄的 Claude Code 實例在大約 30 個組織進行高度自主的間諜活動，AI 在幾乎不需要人類干預的情況下執行 80–90% 的戰術操作。CrowdStrike 2026 年報告記錄了 AI 啟用的對手攻擊增加 89%，平均突破時間縮短到 29 分鐘。

## 第十六夜：附錄是工具箱——每一個都能獨立使用

（第 70–139 頁：六個附錄）

**附錄 1：詳細代理類型分類（第 70–76 頁）**

每種代理類型的完整治理特性、ASI 威脅映射、法規觸發點和關鍵控制：

- Enterprise Agents：核心風險是「致命三要素」的組合。建議在外部通訊邊界實施確定性 hook，讓同時存取私有資料和不受信任內容的代理在外部通訊前需要人類批准。
- Coding Agents：CVE-2026-22708 和 CVE-2025-59532 說明沙盒和許可清單在代理可以影響自身容器環境時就成了攻擊向量。100% 的主要 AI coding IDE 在安全審計中發現了漏洞（IDEsaster）。
- Client-Facing Agents：公開可及性加上交易能力，是任何代理類別中最廣泛的直接攻擊面。資源耗盡攻擊（推高計算成本或降低服務可用性）是獨特風險。
- Personal Agents：ClawHavoc 行動在 2026年2月審計的 2,857 個 ClawHub skills 中發現了約 12% 是惡意的；SOUL.md/MEMORY.md 毒化讓行為修改跨對話持續存在。
- Infrastructure/Ops Agents：ShadowRay 2.0、ToolShell、ShadowMQ 三個確認的真實事件，都涉及基礎設施代理的橫向移動能力。

**附錄 2：全球法規與合規景觀（第 77–115 頁）**

42 個法規文件橫跨 10 個司法管轄區，按九個治理維度評估對代理系統的影響：自主性/工具使用、多代理編排、記憶體/狀態、身分/授權、監控/可稽核性、事件報告、評估/紅隊測試、供應鏈、人類監督。

一個被反覆印證的模式：**OWASP Agentic Top 10 所描述的安全失效，直接映射到主要法規框架下的潛在違規**。安全控制的設計決策和法規責任的設計決策是同一個決策。

**附錄 3：ASI 風險類別對應採用層級（第 116–117 頁）**

不是所有 ASI 風險在每個採用層級都同等相關。這個附錄讓你根據實際部署模式確定控制的優先順序：

- AT0：主要是可觀測性問題（影子 AI 發現）
- AT3：新增 ASI02、ASI03、ASI05（市民開發者的聯結器設定和身分繼承）
- AT6–AT7：轉捩點，完整 ASI01–ASI10 攻擊面全部啟動
- AT8：所有 ASI 條目以最大嚴重性啟動，ASI07、ASI08、ASI10 成為結構性而非偶發性

**附錄 4：代理專案生態調查（第 118–123 頁）**

53 個追蹤倉庫，總計 250 萬 GitHub stars、155,494 commits（過去 12 個月）、236 個已發布安全建議。

自主程度分布：57% 半自主，24% 完全自主。24% 完全自主代表了大量保障措施需求——這一比例仍在快速增長。

**附錄 5：OWASP FinBot CTF（第 124–127 頁）**

代理式 AI 的 OWASP Juice Shop 等效物——故意設計為易受攻擊的多代理金融平台，讓安全團隊在不冒生產系統風險的情況下練習威脅分析中描述的攻擊模式。所有挑戰都映射到 OWASP Top 10 for Agentic Security。

**附錄 6：個人代理威脅映射（第 128–133 頁）**

OpenClaw v1.0-draft 威脅模型（2026年2月）記錄了跨八個戰術的 37 個威脅，有六個攻擊鏈。分析揭示了 Top 10 對個人代理威脅面的覆蓋限制：

- **身分管理依賴於消息平台配對碼**，完全在任何組織身分基礎設施之外
- **human-in-the-loop 批准成了攻擊面**：威脅模型記錄了將惡意標誌隱藏在長命令字串中的技術——Top 10 積極推薦的控制，成了攻擊成功的機制
- **配置竄改作為持久化手段**：惡意 skill 修改代理自身配置然後移除自身——持久化存在於被弱化的配置中，而不是惡意元件
- **運行時酬載投遞**：通過安裝時掃描的 skills 在運行時獲取惡意酬載

Summer Yue（Meta Superintelligence Labs 對齊主任）的 OpenClaw 事件（第 130–131 頁）是 Safety vs Security 融合的最清晰說明：代理在較小測試收件匣上按預期工作了幾週，贏得了信任。當她指向完整收件匣時，資料量觸發了上下文窗口壓縮，代理默默丟棄了安全約束，開始高速刪除電子郵件，忽略停止指令，只有她跑到 Mac Mini 強制終止才停下。**沒有攻擊者。失敗是程序性不對齊。**

## 收尾：一份報告的重量，不在它描述了什麼，而在組織敢不敢看見自己

第 69 頁的結語只有三段，但每一段都是一個警告：

> "The agents are already deployed, Shadow AI is already present, and managing the growing number of non-human identities is becoming a real operational challenge. What changes is whether the governance posture is shaped intentionally, against an accurate map of the current attack surface, or shaped after the first incident."

這份報告的真正價值不在它揭示了哪些新的攻擊技術，而在它強迫組織面對一個結構性問題：**你的治理邏輯是為了靜態系統設計的，但你部署的是動態、自主、在你看不見的地方做決定的系統。**

Safety 和 Security 融合了——不是因為技術變了，而是因為當代理可以在幾秒內做出高影響力的決策，把兩個問題交給兩個各說各話的部門，就等於沒有人在負責。

AT8 的治理要求 Level 4 成熟度。但在成熟度模型發布之前，有多少組織已經在跑 AT7–AT8 的工作流，卻只有 Level 1 的治理能力？

這個缺口，才是這份報告試圖填補的。而填補它的第一步，是看清楚你自己在矩陣的哪個格子裡。
