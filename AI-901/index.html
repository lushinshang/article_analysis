一、 認證變革：AI-900 與 AI-901 核心定位轉變

在微軟的認證體系中，雖然 AI-900 與 AI-901 最終皆指向 Microsoft Certified: Azure AI Fundamentals 這張終身有效的證照，但兩者在考核本質上存在顯著的「範式轉移（Paradigm Shift）」：

關鍵轉變因果鏈

  1. 從「多服務分散」走向「單一平台（Azure AI Foundry）整合」：AI-900 時期考生需記誦 Azure Cognitive Services、Custom Vision、Form Recognizer 等眾多獨立服務名稱；AI-901 則將所有 AI 解決方案的建置、部署與測試流程，收斂至 Azure AI Foundry（前稱 Azure AI Studio/Foundry Portal）。
  2. 從「純理論描述」走向「實作感知（Implementation-Aware）」：AI-901 不再僅考「何謂機器學習」，而是要求考生理解如何透過程式碼或 UI 部署模型、調整模型參數（如 Temperature、Top_P），以及建立 AI 代理人（Agents）。
  3. 從「無 Code」走向「基礎程式碼閱讀（Code Literacy）」：AI-901 正式將 Python SDK 程式碼閱讀能力與 REST API 串接概念納入考綱，要求考生能看懂輕量級用戶端應用的結構與認證機制。

三、 子主題（Sub-objectives）具體學習要求與重點

領域 1：識別 AI 概念與責任 (Identify AI Concepts and Responsibilities) [40–45%]

本領域著重於理論概念與現代生成式 AI 模型基本運作機制的理解。

1.1 負責任的 AI 原則 (Principles of Responsible AI)

  • 學習要求：能根據具體業務場景，識別並應用微軟的六大負責任 AI 原則。
  • 重點知識：
    • 公平性 (Fairness)：確保 AI 系統對所有人一視同仁（避免偏見，如招募 AI 偏好特定性別）。
    • 可靠性與安全性 (Reliability and Safety)：系統在非預期狀況下仍能安全運作，且具備容錯能力。
    • 隱私與安全性 (Privacy and Security)：保護用戶數據，遵循資安合規性。
    • 包容性 (Inclusiveness)：為各類人群（含身障人士）提供無障礙的使用體驗。
    • 透明度 (Transparency)：向用戶解釋 AI 的決策邏輯、模型限制與運作方式。
    • 問責制 (Accountability)：設計者與部署者必須為 AI 系統的行為與後果承擔責任。

1.2 AI 模型元件與配置 (AI Model Components and Configurations)

  • 學習要求：理解生成式 AI 模型的運作原理，並能根據任務需求選擇模型與調整運行參數。
  • 重點知識：
    • 生成式模型原理：Tokens 的概念、上下文窗口（Context Window）的限制，以及 Transformer 架構的基礎預測邏輯。
    • 模型選擇 (Model Selection)：根據任務（文字推理、程式碼生成、數學計算、多模態 Vision/Speech）挑選合適的模型（如 GPT-4o, GPT-4o-mini, Phi-3 等）。
    • 超參數配置：
      • Temperature（溫度）：控制輸出隨機性。數值愈接近 0 愈確定/保守；愈接近 1 愈具創意/隨機。
      • Max Tokens：限制單次生成或回應的最大長度。
      • Top P（核取樣）：與溫度類似，控制候選 Token 的機率範圍。

1.3 AI 工作負載與能力識別 (AI Workloads and Capabilities)

  • 學習要求：識別並區分傳統 ML 工作負載與現代生成式/代理人 AI 工作負載。
  • 重點知識：
    • 傳統 ML：迴歸（Regression）、分類（Classification）、分群（Clustering）。
    • 生成式與代理人 AI (Generative & Agentic AI)：能自主規劃步驟並呼叫工具的 AI 系統。
    • 語音與視覺能力：語音轉文字 (STT)、文字轉語音 (TTS)、影像分類、物件偵測、OCR、人臉分析。

領域 2：使用 Microsoft Foundry 實作 AI 解決方案 (Implement AI Solutions by Using Microsoft Foundry) [55–60%]

本領域為 AI-901 最核心的實作單元，考生需熟悉 Azure AI Foundry 的操作流程及程式碼實作。

2.1 生成式 AI 應用與代理人實作 (Generative AI Apps and Agents)

  • 學習要求：掌握提示詞工程，並能在 Azure AI Foundry Portal 及 SDK 中部署模型與代理人。
  • 重點知識：
    • 提示詞設計 (Prompt Engineering)：區分系統提示詞（System Prompts）（設定 AI 的角色、語氣與邊界條件）與使用者提示詞（User Prompts）。
    • Foundry Portal 操作：理解 Hubs（資源管理中心）、Projects（專案開發空間）、Model Catalog（模型目錄部署）與 Playground（沙盒測試環境）的層級關係。
    • Python SDK 基礎呼叫：考生必須能夠閱讀並理解以下 azure-ai-projects 與 azure-ai-inference SDK 的典型代碼結構：
import os
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.ai.inference.models import SystemMessage, UserMessage

# 1. 初始化專案用戶端 (使用 Entra ID 認證)
project_endpoint = os.environ.get("FOUNDRY_PROJECT_ENDPOINT")

with DefaultAzureCredential() as credential:
    with AIProjectClient(endpoint=project_endpoint, credential=credential) as project_client:

        # 2. 獲取 Chat 推論用戶端
        chat_client = project_client.inference.get_chat_completions_client()

        # 3. 呼叫部署的模型進行推論
        response = chat_client.complete(
            model="gpt-4o-mini-deployment",
            messages=[
                SystemMessage(content="你是一位專業的微軟認證講師。"),
                UserMessage(content="請簡述 AI-901 的及格分數是多少？")
            ]
        )
        print(response.choices[0].message.content)
  • AI 代理人 (Agents) 配置：理解如何建立 Agent、管理 Thread（對話階段）與 Run（執行）。
    • 考生需理解以下 Agent 建立與執行的 SDK 流程：
# 在 project_client 上建立 Agent
agent = project_client.agents.create_agent(
    model="gpt-4o-mini",
    name="exam-helper-agent",
    instructions="協助考生解答 Azure AI-901 的問題。"
)

# 建立獨立的 Conversation Thread
thread = project_client.agents.create_thread()

# 在 Thread 中建立 Message
message = project_client.agents.create_message(
    thread_id=thread.id,
    role="user",
    content="請問 Agentic AI 是什麼？"
)
  • 內建 Agent 工具：掌握 file_search（向量檢索/RAG）與 code_interpreter（程式碼解釋器，用於數學計算或數據分析）的啟用時機。

2.2 文字與語音解決方案實作 (Text and Speech Solutions)

  • 學習要求：實作文字分析與語音合成/辨識的應用串接。
  • 重點知識：
    • 使用 TextAnalyticsClient 進行實體辨識、關鍵字擷取與情感分析。
    • 整合 Azure Speech 服務，處理語音提示詞並透過多模態模型產生回應。

2.3 實務開發技能與驗證 (Practical Development Skills)

  • 學習要求：理解用戶端應用程式如何安全地與 Azure AI Foundry 服務互動。
  • 重點知識：
    • 認證機制：強烈建議使用 Microsoft Entra ID（搭配 DefaultAzureCredential）進行無金鑰驗證，取代傳統的 API Key 驗證以提升安全性。
    • 資源組態：理解 Endpoints（端點）與 API 版本（API Version）在連接服務時的作用。

2.4 電腦視覺、圖像生成與資訊提取 (Vision, Image Generation & Extraction)

  • 學習要求：利用視覺模型進行物件分析，並能從非結構化文檔中提取結構化資訊。
  • 重點知識：
    • 利用 DALL-E 3 進行圖像生成與編輯的基礎呼叫概念。
    • Azure AI Content Understanding / Document Intelligence：理解如何分析表單、發票、身份證明文件，並將非結構化影像/PDF 轉換為結構化 JSON 輸出。

一、 六大原則定義、實施準則與 Azure 工具對照

負責任 AI 原則 原則定義 (Definition) 微軟實施準則 (Guidelines) Azure 對應檢測或控制工具
公平性
(Fairness)		 AI 系統應以公平的方式對待所有人，避免因性別、種族、年齡或身心障礙等人口特徵造成不合理的偏誤或歧視。 1. 跨人口族群評估模型輸出與預測結果。
2. 確保訓練數據具備多樣性與代表性。
3. 使用演算法主動降低模型偏見。		 1. Fairlearn (與 Azure ML 整合)：分析並減輕模型在不同人口統計群體間的效能偏差（如差異準確率、選擇率等）。
2. Azure AI Content Safety：過濾與偵測仇恨言論 (Hate speech) 與偏見言論。
可靠性與安全性
(Reliability & Safety)		 AI 系統應在預期條件下穩定運作，具備高韌性，且在面對異常或對抗性攻擊時能安全退避，避免造成實體或心理傷害。 1. 於不同、極端或惡劣的條件下進行系統測試。
2. 實施容錯與降級機制 (Fail-safe)。
3. 部署後持續監控以防範非預期失敗。		 1. Azure ML Model Monitoring：監控資料漂移 (Data Drift) 與模型效能下降。
2. Azure Chaos Studio：注入混亂與故障以測試 AI 系統架構的穩定度與復原力。
3. Azure AI Content Safety：偵測並阻斷危害身心安全的內容（如自殘 Self-harm、暴力 Violence）。
隱私權與安全性
(Privacy & Security)		 AI 系統應嚴格保護個人隱私與敏感資料，防止未經授權的存取、數據外洩或竄改，並符合國際合規法規。 1. 加密敏感與個資數據（靜態與傳輸中）。
2. 實施角色型存取控制 (RBAC) 與最小權限原則。
3. 採用差分隱私或去識別化技術。		 1. Azure Key Vault：安全儲存金鑰、連接字串與憑證。
2. Azure RBAC：精細控制機器學習工作區與資料存取權限。
3. Microsoft Purview：資料分類、機密性標籤與合規性稽核。
4. Azure Private Endpoint & VNet：在隔離網路中執行 AI 推論，防止公開暴露。
包容性
(Inclusiveness)		 AI 系統應設計為能讓所有不同能力、語言背景與需求的人都能參與並從中受益，打破數位與生理障礙。 1. 遵循無障礙網頁規範（如 WCAG 2.1）。
2. 支援多語言、在地化與語音輔助介面。
3. 設計時納入多元背景使用者的回饋。		 1. Azure AI Vision (OCR / Image Captioning)：為影像自動產生文字描述，供螢幕閱讀器使用，協助視障者。
2. Azure AI Speech (TTS / STT)：將文字轉語音、語音轉文字，為有語言或聽力障礙的使用者提供輔助功能。
3. Azure AI Translator：提供即時多語系翻譯。
透明度
(Transparency)		 AI 系統的運行方式與決策邏輯應是可理解且可解釋的。使用者應知悉自己正在與 AI 互動，並了解系統的能力與限制。 1. 向使用者說明預測與決策是如何產生的。
2. 明確告知使用者正在與 AI 系統互動。
3. 發布透明度備忘錄 (Transparency Note) 說明系統極限。		 1. InterpretML (與 Azure ML 整合)：提供黑箱模型的解釋功能（如 SHAP、LIME），可視化各特徵對預測結果的貢獻值。
2. Azure ML Model Registry Lineage：追蹤模型資產的生命週期，從數據源、訓練程式碼到部署端點的完整軌跡。
責任歸屬
(Accountability)		 設計、部署和運行 AI 系統的個人與組織，必須對系統的運作方式、決策結果以及對社會造成的影響負起最終責任。 1. 實施「人在迴圈 (Human-in-the-loop)」監督機制。
2. 建立 AI 治理審查委員會。
3. 揭露系統的開發團隊與稽核軌跡，以利追蹤。		 1. Azure AI Document Intelligence (Human-in-the-loop)：整合人工校對工作流，將低信賴度的 AI 辨識結果轉交人工審核。
2. Azure Policy / Microsoft Purview：實施強制性合規原則與稽核日誌 (Audit Logs)，追蹤所有模型操作與發布紀錄。

二、 Azure AI Content Safety Python SDK 程式碼實作

微軟提供了 Azure AI Content Safety 服務，可用於檢測有害的文字與影像內容。以下是使用 Python SDK 進行文字與影像安全偵測的基礎實作範例。

1. 安裝必要套件

在使用前，請確保已安裝 Azure AI Content Safety 用戶端程式庫：

pip install azure-ai-contentsafety azure-core

2. Python 完整範例程式碼

[!IMPORTANT] 執行此程式碼前，需在 Azure 入口網站建立 Azure AI Content Safety 資源，並獲取對應的 ENDPOINT 與 KEY。

import os
from azure.ai.contentsafety import ContentSafetyClient
from azure.core.credentials import AzureKeyCredential
from azure.core.exceptions import HttpResponseError
from azure.ai.contentsafety.models import (
    AnalyzeTextOptions,
    AnalyzeImageOptions,
    ImageData
)

# 1. 初始化 Content Safety 用戶端
# 請將實體端點與金鑰替換為您的 Azure 資源資訊
ENDPOINT = os.getenv("AZURE_CONTENT_SAFETY_ENDPOINT", "https://<your-resource-name>.cognitiveservices.azure.com/")
KEY = os.getenv("AZURE_CONTENT_SAFETY_KEY", "<your-subscription-key>")

credential = AzureKeyCredential(KEY)
client = ContentSafetyClient(endpoint=ENDPOINT, credential=credential)

def analyze_text_content(text_to_test: str):
    """
    使用 SDK 偵測有害文字內容。
    偵測類別包括：HateSpeech (仇恨言論)、SelfHarm (自殘)、Sexual (性暗示)、Violence (暴力)
    """
    print(f"\n[開始文字偵測] 輸入內容: '{text_to_test}'")

    # 建立文字分析請求
    options = AnalyzeTextOptions(text=text_to_test)

    try:
        response = client.analyze_text(options)

        print("--- 文字偵測結果 ---")
        # 遍歷四大有害類別的檢測結果
        # severity (嚴重程度評分) 範圍為 0-7；0 代表安全，數字愈大愈危險
        for category_analysis in response.categories_analysis:
            print(f"類別: {category_analysis.category:<12} | 嚴重程度評分: {category_analysis.severity}")

    except HttpResponseError as e:
        print(f"文字分析失敗，錯誤代碼: {e.status_code}, 訊息: {e.message}")


def analyze_image_content(image_path: str):
    """
    使用 SDK 偵測有害影像內容。
    輸入需為圖片的二進位資料。
    """
    print(f"\n[開始影像偵測] 圖片路徑: '{image_path}'")

    if not os.path.exists(image_path):
        print(f"錯誤：找不到圖片檔案 {image_path}")
        return

    try:
        # 讀取圖片的二進位資料
        with open(image_path, "rb") as image_file:
            image_bytes = image_file.read()

        # 建立影像分析請求，將二進位資料封裝入 ImageData
        options = AnalyzeImageOptions(image=ImageData(content=image_bytes))

        response = client.analyze_image(options)

        print("--- 影像偵測結果 ---")
        for category_analysis in response.categories_analysis:
            print(f"類別: {category_analysis.category:<12} | 嚴重程度評分: {category_analysis.severity}")

    except HttpResponseError as e:
        print(f"影像分析失敗，錯誤代碼: {e.status_code}, 訊息: {e.message}")
    except Exception as e:
        print(f"執行發生非預期錯誤: {e}")


if __name__ == "__main__":
    # 測試有害文字偵測

3. 有害類別與嚴重度說明

Azure AI Content Safety 主要偵測以下四大威脅類別： 1. HateSpeech (仇恨言論)：針對種族、宗教、性別、性傾向或身心障礙等群體進行攻擊、貶低或歧視的語言。 2. SelfHarm (自殘)：鼓勵、指導或描述自殺、自殘或飲食失調的行為。 3. Sexual (性暗示/色情)：描述性器官、性行為或高度露骨的性暗示內容。 4. Violence (暴力)：描繪實體傷害、殺人、武器使用或宣揚暴力的情境。

AI-901 認證準備研究報告：識別 AI 模型的組件與配置

本報告深入探討 AI-901（Microsoft Azure AI Fundamentals 升級與實務相關主題）中「識別 AI 模型的組件與配置」的核心知識點，結合 index.html 中的實際考題進行深度剖析，並提供 Azure AI 模型的 Python SDK 配置範例。

壹、 核心概念與認證考點深析

在機器學習與生成式 AI 的工作流程中，理解模型從數據處理、參數設定到訓練與微調的各個階段是通過 AI-901 認證的基石。以下為核心概念的定義與考點整理：

1. 特徵工程 (Feature Engineering)

  • 定義：將原始數據進行清洗、轉換、組合與篩選，以產生更適合機器學習模型訓練的「特徵 (Features)」的過程。這能直接決定模型的上限。
  • 核心考點與常用方法：
    • 特徵縮放 (Feature Scaling)：例如 Min-Max 歸一化（將數值壓縮至 0 到 1）或標準化 (Standardization)（轉換為平均值 0、標準差 1 的分佈）。其目的是防止數值範圍過大的特徵主導模型的梯度更新。
    • 獨熱編碼 (One-Hot Encoding)：將類別型數據（如：城市「台北、台中、高雄」）轉換為二進位向量，避免模型誤將類別型序號視為有大小順序的數值。
    • 缺失值補植 (Imputation)：使用平均數、中位數、眾數或特定演算法填補數據空值。
    • 降維 (Dimensionality Reduction)：如主成分分析 (PCA)，在保留最大變異量的前提下減少特徵維度。
    • Azure 實務相關：在 Azure Automated ML (自動化機器學習) 中，系統會自動執行特徵建構與補植（稱為 Featurization），使用者僅需開啟此配置即可。

2. 超參數 (Hyperparameters)

  • 定義：在模型訓練開始之前手動設定的配置參數。超參數控制著訓練的過程與模型結構，無法從訓練數據中直接學習與更新（與模型內部的「權重 Weights」和「偏差 Biases」不同）。
  • 核心考點：
    • 常見超參數：學習率 (Learning Rate)、批次大小 (Batch Size)、訓練輪數 (Epochs)、決策樹的最大深度 (Max Depth)、正則化係數（L1/L2）。
    • 超參數調優 (Hyperparameter Tuning / Sweeping)：在 Azure ML 中，使用 HyperDrive 來自動搜尋最優超參數組合。
    • 搜尋取樣方式：網格取樣 (Grid Sampling)、隨機取樣 (Random Sampling)、貝氏取樣 (Bayesian Sampling)。
    • 早停原則 (Early Termination Policy)：當某組超參數表現不佳時提前中止以節省運算成本。常見政策包括 Bandit Policy（基於與目前最佳模型的鬆弛因子比較）、Median Stopping Policy（低於歷史運作的中位數則中止）和 Truncation Selection Policy。

3. 訓練/驗證/測試集劃分 (Train/Validation/Test Split)

  • 定義：為了評估模型的泛化能力並防止過擬合 (Overfitting)，將原始數據集劃分為三個彼此互斥的子集。
  • 各子集職責與考點： 
    graph TD
    A[原始數據集] --> B[訓練集 Train Set]
    A --> C[驗證集 Validation Set]
    A --> D[測試集 Test Set]
    B -->|更新模型權重/參數| E[模型訓練]
    C -->|評估表現並調整超參數| F[超參數調優]
    D -->|最終評估泛化效能| G[獨立測試]
    • 訓練集 (Train Set)：佔比最大（通常 70%-80%），用於訓練模型以更新其內部的參數（權重與偏差）。
    • 驗證集 (Validation Set)：在訓練過程中頻繁使用，用於評估模型效能並指導超參數（如學習率、深度）的調整，以防止模型過度擬合訓練集。
    • 測試集 (Test Set)：在模型訓練與調優完全結束後，僅使用一次來評估模型的最終表現。測試集絕對不能參與模型的任何訓練或超參數調整決策。

4. 遷移學習 (Transfer Learning)

  • 定義：將已經在大型通用數據集上訓練好的模型（即基礎模型 Foundation Model，例如 ResNet、BERT、GPT）之「知識」（權重與特徵提取能力），轉移應用到另一個規模較小但相關的新任務中。
  • 核心考點：
    • 優勢：在目標領域數據有限、算力不足時，能夠大幅減少訓練時間並提高模型準確率。
    • 方法：
      1. 特徵提取 (Feature Extraction)：凍結預訓練模型的全部或大部分權重，僅訓練新添加的輸出層（分類器）。
      2. 微調 (Fine-tuning)：允許更新預訓練模型的部分或全部權重。

5. 微調 (Fine-tuning)

  • 定義：遷移學習的一種具體實踐。在保留基礎預訓練模型的通用知識的前提下，使用特定任務的標記數據集對模型進行額外的梯度更新（訓練），以適應該特定任務的輸出風格、格式或領域知識。
  • 核心考點：
    • 微調 vs 提示工程 (Prompt Engineering) / 檢索增強生成 (RAG)：
      • 微調會修改模型的權重 (Weights)。適用於改變模型的行為模式、回應語氣、遵循複雜格式或在無上下文提示下學習特定領域特徵。
      • RAG與提示工程不會改變模型權重，而是透過上下文注入最新的外部動態資料。
    • 部署關係：在 Azure AI Foundry 中，微調是選用步驟。許多基礎模型可以直接部署與呼叫，不需要先經過微調或重新訓練。

貳、 機器學習常用模型評估指標 (Evaluation Metrics)

在 AI-901 認證中，能夠針對不同的任務情境選擇並解讀正確的評估指標是極高頻的考點。

1. 監督式學習：迴歸模型指標 (Regression Metrics)

迴歸任務旨在預測連續數值。設 $y_i$ 為真實值，$\hat{y}_i$ 為預測值，$\bar{y}$ 為真實值的平均值，共有 $n$ 個樣本。

指標名稱 英文全稱 數學定義 核心特點與認證考點
平均絕對誤差 Mean Absolute Error (MAE) $\text{MAE} = \frac{1}{n}\sum_{i=1}^n \vert y_i - \hat{y}_i \vert$ 1. 單位與預測目標相同，直觀易懂。
2. 對異常值 (Outliers) 的敏感度呈線性，不會過度放大極端誤差。
均方根誤差 Root Mean Squared Error (RMSE) $\text{RMSE} = \sqrt{\frac{1}{n}\sum_{i=1}^n (y_i - \hat{y}_i)^2}$ 1. 因為包含平方項，對較大誤差/異常值的懲罰極重。
2. 若系統要求「絕對不能出現極端預測錯誤」，通常以 RMSE 為優化指標。
決定係數 R-squared ($R^2$) $R^2 = 1 - \frac{\sum(y_i - \hat{y}_i)^2}{\sum(y_i - \bar{y})^2}$ 1. 數值範圍通常在 0 到 1 之間（若預測比平均值還差則可能為負）。
2. 代表模型能解釋目標變數變異量的比例。越接近 1 擬合度越高。

2. 監督式學習：分類模型指標 (Classification Metrics)

分類任務旨在預測類別（以二分類為例，關注陽性 Positive 與陰性 Negative）。

混淆矩陣基礎：

  • TP (True Positive)：實際為正，預測為正。
  • FP (False Positive，偽陽性)：實際為負，預測為正。（誤判，例如垃圾郵件過濾器把好信當成垃圾信）
  • TN (True Negative)：實際為負，預測為負。
  • FN (False Negative，偽陰性)：實際為正，預測為負。（漏判，例如癌症篩檢沒驗出來）

核心指標對比：

  • 準確率 (Accuracy)： $$\text{Accuracy} = \frac{TP + TN}{TP + TN + FP + FN}$$
    • 考點：在樣本不均衡 (Imbalanced Dataset) 時（例如 99% 為正常交易，1% 為詐騙），這個指標會嚴重失真（即使模型全部猜正常，準確率也有 99%）。
  • 精確率 (Precision，陽性預測值)： $$\text{Precision} = \frac{TP}{TP + FP}$$
    • 考點：關注「在所有被模型預測為正的樣本中，真正為正的比例」。旨在最小化偽陽性 (FP)。
    • 適用場景：垃圾郵件過濾（不能把重要信件判為垃圾信）、司法判決（不能冤枉好人）。
  • 召回率 (Recall / Sensitivity，敏感度)： $$\text{Recall} = \frac{TP}{TP + FN}$$
    • 考點：關注「在所有實際為正的樣本中，被模型正確找出來的比例」。旨在最小化偽陰性 (FN)。
    • 適用場景：傳染病篩檢（不能漏掉任何患者）、金融信用卡詐騙偵測（寧可錯殺不可漏過）。
  • F1-score： $$\text{F1} = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$$
    • 考點：Precision 與 Recall 的調和平均數。當兩者存在權衡（Trade-off）且數據分佈不均勻時，F1-score 是最客觀的綜合評估指標。
  • ROC 曲線與 AUC (Area Under Curve)：
    • ROC 曲線：以真陽性率 (TPR = Recall) 為縱軸，假陽性率 (FPR = $FP / (TN + FP)$) 為橫軸繪製的曲線。
    • AUC：ROC 曲線下的面積。範圍在 0.5（隨機猜測）到 1.0（完美分類）之間。AUC 具有分類閾值不變性，用於評估模型對正負樣本的排序區分能力。

3. 非監督式學習：聚類模型指標 (Clustering Metrics)

聚類任務旨在將無標籤的數據分組。

  • 輪廓係數 (Silhouette Coefficient)：
    • 計算單個樣本與同集群內其他樣本的平均距離（凝聚度 $a$），以及與最近鄰集群樣本的平均距離（分離度 $b$）。
    • 單一物體輪廓係數為：$s = \frac{b - a}{\max(a, b)}$。整體模型指標為所有樣本輪廓係數的平均值。
    • 數值解讀：
      • 接近 1：代表集群內部凝聚力高，且集群之間分界明顯，聚類效果極佳。
      • 接近 0：代表樣本位於兩個集群的邊界重疊處。
      • 接近 -1：代表樣本被分錯到了錯誤的集群中。
  • Davies-Bouldin Index (DBI)：
    • 計算任意兩個集群的類內距離之和與類間距離之比的最大值。
    • 數值解讀：數值越小，代表集群內部越緊密，且集群間分離度越大，聚類效果越好。

Azure AI Foundry 核心架構與安全實務：AI-901 備考指南

本文件深入剖析 Azure AI Foundry（前身為 Azure AI Studio）的核心架構組成，並針對 AI-901「透過使用 Microsoft Foundry 實施 AI 解決方案」考綱，整理出架構設計、安全存取與認證、Python SDK 實作，以及佈署管理的必考重點。

一、 Azure AI Foundry 核心組成架構

Azure AI Foundry 是企業級生成式 AI 與機器學習解決方案的統一開發平台。其架構設計旨在分離資源治理/管理（Hub）與開發協作（Project），並透過連接（Connections）與模型型錄（Model Catalog）加速 AI 應用的開發與佈署。

1. 核心元件關係與架構圖

Azure AI Foundry 的階層關係如下：

graph TD
    subgraph AzureSub["Azure Subscription"]
        Hub[Azure AI Foundry Hub 中樞]
        Hub -->|繼承安全與計費| ProjectA[Project 專案 A]

    end

    ProjectA -->|開發與評估| Playground[Playgrounds & Prompt Flow]
    ProjectA -->|模型佈署| Endpoints[Endpoints - Serverless / Managed]

2. Hub (中樞)

  • 定位：Hub 是 Azure AI Foundry 的最頂層管理容器，對應於 Azure Resource Manager (ARM) 中的資源類型為 Microsoft.MachineLearningServices/workspaces（類型標記為 Hub）。
  • 職責：
    • 資源與安全性控管：定義網路邊界、虛擬網路 (VNet) 設定、加密金鑰 (Customer-Managed Keys, CMK) 及安全原則。
    • 集中計費：與之關聯的 Azure 訂用帳戶 (Subscription) 與資源群組 (Resource Group) 會在此層級進行費用彙整。
    • 關聯資源 (Associated Resources)：創建 Hub時，必須關聯或新建以下資源：
      • Azure Storage Account：儲存專案的實驗成品、代碼、提示流程 (Prompt Flow) 資料。
      • Azure Key Vault：安全儲存連接密鑰與憑證。
      • Azure Container Registry (ACR)：存放用於自訂計算或佈署的 Docker 映像檔。
      • Application Insights（選配）：監控運行時期的效能與日誌。
    • 共享資源：在 Hub 創建的 Connections 可以共享給旗下所有 Projects，避免重複設定。

3. Project (專案)

  • 定位：Project 是協作與開發的工作區（對應 ARM 資源亦為 workspaces，但類型標記為 Project）。Project 必須隸屬於某個 Hub，無法單獨存在。
  • 職責：
    • 成員協作：開發人員在 Project 中建立 Prompt Flow、上傳資料集、進行模型微調 (Fine-tuning)、運行評估 (Evaluations) 以及佈署終端節點 (Endpoints)。
    • 資源隔離：不同專案間的資料與實驗是相互隔離的，但會繼承所屬 Hub 的安全與網路設定。
    • 專案專屬 Connections：除了使用 Hub 的共享連接外，專案可以建立專屬的連接（例如特定外部 API），此連接對其他專案不可見。

4. Connections (連接/連線)

  • 定位：Connections 是 Azure AI Foundry 與外部或 Azure 內部服務之間進行安全通訊的配置物件。
  • 支援的服務：
    • Azure OpenAI Service
    • Azure AI Search
    • Azure AI Services (多功能合一服務)
    • 外部 API (如 Cohere, Mistral 等第三方託管 API)
    • 自訂資料來源 (Microsoft OneLake, Azure Blob Storage 等)
  • 認證機制 (Credentials)：
    • API Key / Access Token：最傳統的連接方式，密鑰會被加密儲存於 Hub 關聯的 Azure Key Vault 中。
    • Microsoft Entra ID (舊稱 Azure AD)：利用託管識別 (Managed Identity) 進行無密鑰 (Keyless) 連接，是企業安全架構與考試推薦的首選。

5. Model Catalog (模型型錄)

  • 定位：Azure AI Foundry 的集中化模型市集，提供開源與專有模型的探索、評估與佈署。
  • 佈署模式 (Deployment Modes)：
    1. 無伺服器 API (Serverless APIs / Model-as-a-Service, MaaS)：
      • 特點：無需管理底層計算資源 (VM)。按使用量 (Tokens) 計費。
      • 適用對象：大部分 OpenAI 模型，以及經由 Azure 託管的 Llama 3、Mistral 等開源模型。
      • 優勢：快速上線、零維護成本、隨用隨付。
    2. 受控計算 (Managed Compute)：
      • 特點：將模型佈署到專用的 Azure 虛擬機器 (VM) 實例上。依據所選 VM 的規格與運行時間 (Pay-by-hour) 計費。
      • 適用對象：需要對模型進行深度微調 (Fine-tuning)、需要極高且穩定的吞吐量 (Throughput)、或法規要求計算資源必須完全隔離的場景。

二、 安全存取與認證管理

安全存取是企業實施 AI 解決方案的核心要素。Azure AI Foundry 主要透過 Azure 角色型存取控制 (RBAC) 與受控識別 (Managed Identities) 來達成最小權限原則與網路隔離。

1. 關鍵 RBAC 角色

在實作與考試中，必須分清以下角色的職責與權限範圍：

角色名稱 權限範圍 適用情境
Azure AI Developer 可以在 Project 中建立、更新、刪除 AI 資源（如 Flow、Deployments）。 開發團隊成員的日常角色。
Cognitive Services OpenAI User 僅允許呼叫 Azure OpenAI 的 API 進行推理（Inference）。 應用程式端點、開發者測試 API 用。
Cognitive Services Contributor 允許建立、管理及刪除 Azure OpenAI/AI Services 執行個體。 雲端架構師或 CI/CD 流水線。
Storage Blob Data Contributor 讀寫 Azure Storage Account 中的 Blob 資料。 需授予 Hub 的受控識別，以便寫入實驗結果。

2. 受控識別 (Managed Identities) 在連線中的角色

為了避免在程式碼或環境變數中硬編碼 API Key，應優先使用受控識別： * 系統指派受控識別 (System-assigned Managed Identity)： * 生命週期與 Hub/Project 綁定。 * 當 Hub 被刪除時，該識別自動被刪除。 * 使用者指派受控識別 (User-assigned Managed Identity)： * 獨立的 Azure 資源，生命週期獨立。 * 可同時指派給多個資源（如多個 Hub 或多個虛擬機器）。 * 授權流程： 1. 啟用 Azure AI Hub/Project 的受控識別。 2. 在目標資源（如 Azure OpenAI 或 Azure AI Search）上，透過 IAM 將 Cognitive Services OpenAI User 或 Search Index Data Reader 角色授予該受控識別。 3. 程式端使用無密鑰方式 (Keyless Connection) 進行存取。

3. 網路隔離與專用存取

  • 虛擬網路 (VNet)：將 Hub 設定在私人虛擬網路內，限制僅能透過特定網路路徑存取。
  • 私人端點 (Private Endpoints)：為 Hub、Storage Account、Key Vault 建立 Private Endpoint，確保所有的控制面與資料面流量皆走 Azure 骨幹網路 (ExpressRoute 或 VPN)，而不暴露於公共網際網路。

三、 Python SDK (azure-ai-projects) 實作範例

以下說明如何使用最新版的 Python SDK (azure-ai-projects) 來連線至 Azure AI Foundry 專案，並列出可用連線以及呼叫模型。

1. 前置作業與安裝

在使用 Python SDK 之前，請確保已安裝相關套件，並設定好 Azure CLI 認證：

pip install azure-ai-projects azure-identity

2. 連線與基本設定程式碼範例

本範例展示如何使用 DefaultAzureCredential 進行無密鑰身份驗證，連線至專案，並檢索底層連線資訊。

import os
from azure.identity import DefaultAzureCredential
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import ConnectionType

# 1. 設定環境變數或直接帶入連線字串 (Connection String)
# 連線字串格式通常為: <region>.api.azureml.ms;subscription=<sub_id>;resource-group=<rg>;project=<project_name>
project_connection_string = os.environ.get(
    "AZURE_AI_PROJECT_CONNECTION_STRING",
    "eastus2.api.azureml.ms;subscription=00000000-0000-0000-0000-000000000000;resource-group=my-ai-rg;project=my-ai-project"
)

# 2. 初始化認證物件 (優先使用預設 Azure 認證，如 Azure CLI, Managed Identity 等)
credential = DefaultAzureCredential()

def main():
    print("正在初始化 AI Project Client...")
    # 3. 建立專案用戶端
    project_client = AIProjectClient.from_connection_string(
        credential=credential,
        conn_str=project_connection_string
    )

    # 獲取專案基本資訊
    project_info = project_client.scope
    print(f"成功連線至專案: {project_info.get('project_name')}")
    print(f"訂用帳戶 ID: {project_info.get('subscription_id')}")
    print(f"資源群組: {project_info.get('resource_group_name')}\n")

    # 4. 獲取專案中設定的服務連線 (Connections)
    print("--- 查詢專案中已建立的 Connections ---")
    connections = project_client.connections.list()
    for conn in connections:
        print(f"名稱 (Name): {conn.name}")
        print(f"類型 (Type): {conn.connection_type}")
        print(f"端點 (Endpoint): {conn.endpoint}")
        print(f"驗證類型 (Auth Type): {conn.auth_type}")
        print("-" * 30)

    # 5. 實務情境：獲取預設的 Azure OpenAI 連線並取得 chat client
    try:
        # 列出專案中的 Azure OpenAI 連線
        aoai_connection = project_client.connections.get_default(
            connection_type=ConnectionType.AZURE_OPEN_AI
        )
        print(f"\n成功取得預設 Azure OpenAI 連線: {aoai_connection.name}")

        # 使用專案用戶端快速取得 OpenAI 整合的 Chat 服務 (需配合 openai SDK)
        # 註：在 azure-ai-projects SDK 中，可透過專案直接獲取推論端點
        print("準備呼叫模型推論...")

    except Exception as e:
        print(f"\n無法取得預設 Azure OpenAI 連線，請確認專案中是否已設定。錯誤: {e}")

if __name__ == "__main__":
    main()

[!TIP] 無密鑰實踐 (Keyless Best Practice)： 在上述程式碼中，DefaultAzureCredential() 會在本地自動搜尋 az login 取得的認證；而在 Azure 雲端環境（如 Azure App Service, Azure Container Apps 或 Azure VM）運行時，它會自動偵測並使用該環境的 Managed Identity。

四、 AI-901 考試考點整理：佈署與管理

在 AI-901 考試中，「透過使用 Microsoft Foundry 實施 AI 解決方案」通常著重於資源結構設計、安全邊界劃分、成本控制以及連線設定。以下為四大核心考點與解題邏輯：

考點 1：Hub 與 Project 的資源繼承與邊界

  • 典型考題：
    • 「公司有三個開發團隊，需要使用同一個訂用帳戶，但彼此的數據與實驗必須隔離，且需要共享同一個企業 Azure AI Search 索引。你該如何規劃資源？」
  • 解題邏輯：
    • 建立 1 個 Hub 以進行集中計費、網路安全設定。
    • 在該 Hub 中設定與 Azure AI Search 的 Shared Connection。
    • 為三個團隊建立 3 個 Projects，均歸屬於該 Hub。
    • 重點：Project 會自動繼承 Hub 的 VNet、Storage Account 與 Shared Connections，但 Project 內部的 Prompt Flow 與實驗資料互相隔離。

考點 2：安全性與認證模式選擇 (Key vs. Managed Identity)

  • 典型考題：
    • 「你需要確保連線至 Azure OpenAI 的 API 金鑰不會暴露在程式碼中，且符合企業安全性合規要求。應使用哪種驗證方式？」
  • 解題邏輯：
    • 優先選擇 Microsoft Entra ID (Managed Identity) 認證，而非 API Key。
    • 考試中若出現「最小權限原則」，答案通常是將 Cognitive Services OpenAI User 角色指派給 Project 的受控識別，而不是賦予 Contributor（擁有者/參與者）權限。

考點 3：MaaS (Serverless API) 與 Managed Compute (自建計算) 的佈署抉擇

  • 典型考題：
    • 「團隊需要測試多個 Llama 3 模型，每天僅呼叫幾百次，希望成本降到最低。你該選擇哪種佈署模式？」
    • 「你需要對 Mistral 模型進行大規模微調，且需要保證極高的每秒查詢數 (QPS)，同時預算充足。你該選擇哪種佈署模式？」
  • 解題邏輯：
    • 低用量、快速測試、Token 計費 $\rightarrow$ 選擇 Serverless API (Model-as-a-Service, MaaS)。
    • 深度微調、穩定吞吐量、獨佔 VM、時間計費 $\rightarrow$ 選擇 Managed Compute (託管計算)。

考點 4：網路安全與 Private Endpoint

  • 典型考題：
    • 「如何防止 Azure AI Foundry 的資料面流量流向公共網際網路？」
  • 解題邏輯：
    • 在 Hub 上設定 Private Endpoint (私人端點)，並停用 Public Network Access。
    • 確保關聯的 Azure Storage Account 與 Key Vault 同時啟用私人存取權限。

AI-901 考前研究報告：透過 Foundry 實現電腦視覺與影像生成解決方案

本研究報告針對 AI-901 認證考綱中的「透過使用 Foundry 實現具備電腦視覺與影像生成能力的 AI 解決方案」進行深度剖析。內容包含 Azure AI Vision 各項視覺技術的核心概念與考點、最新 Python SDK 的實作範例，以及對 index.html 中 8 道 vision-foundry 類別考古題的解構與結構化因果鏈分析。

一、 Azure AI Vision & 影像生成核心概念與考點

Azure AI 提供了豐富的電腦視覺與影像生成工具。在 Microsoft Foundry 與 Azure AI Studio 的整合環境中，這些技術被歸類為不同的 AI 工作負載，其核心觀念與常見考點整理如下：

1. 影像分析 (Image Analysis)

  • 核心概念：影像分析旨在從單一影像中擷取多種視覺特徵（Visual Features）。
  • 關鍵功能 (Visual Features)：
    • Tags（標籤）：識別影像中的數千個可識別物件、生物、風景和動作，並為每個標籤提供信賴度分數。
    • Objects（物件偵測）：找出影像中的特定物件，並為每個物件標示標籤與邊界框 (Bounding Box) 座標。
    • Caption（說明文字）：生成一段完整、符合文法的中文/英文句子，對整個影像內容進行人類可讀的摘要描述。
    • DenseCaptions（密集說明文字）：為影像的多個子區域產生局部的說明文字，並給出對應的邊界框。
    • Read (OCR)：偵測並擷取影像或掃描文件中的印刷體和手寫文字。
    • People（人物偵測）：偵測影像中的人物，並為其標示邊界框。
    • SmartCrops（智慧裁切）：分析影像的顯著區域，產生適合特定長寬比的裁切框。
  • 重要考點：
    • 多模態模型 vs. 專屬電腦視覺模型：專屬的 Azure AI Vision 模型在 OCR、密集說明文字、智慧裁切等特定任務上效率極高；而多模態大模型（如 GPT-4o with Vision）在理解上下文、推理和複雜問答上更具優勢。
    • 請求參數：在 SDK 呼叫中，必須在 visual_features 參數中明確指定要擷取的特徵（例如 VisualFeatures.TAGS、VisualFeatures.OBJECTS），否則不會返回對應的資料。

2. 影像分類 (Image Classification) vs. 物件偵測 (Object Detection)

  • 影像分類 (Image Classification)：
    • 概念：判定整張圖片屬於哪一個（或哪幾個）預定義的類別。
    • 考點：影像分類只針對整個影像輸出一個或多個標籤，不提供這些標籤代表的物件在影像中的具體空間位置（無座標/無邊界框）。
  • 物件偵測 (Object Detection)：
    • 概念：在影像中找出特定的物件，並提供其類別以及在影像中的精確位置。
    • 考點：輸出包含 標籤 (Label)、信賴度 (Confidence) 和 邊界框 (Bounding Box)。邊界框通常以 [x, y, w, h]（左上角座標及寬高）表示。
  • 技術對比表：
比較維度 影像分類 (Image Classification) 物件偵測 (Object Detection)
處理目標 判斷「這張圖是什麼？」 判斷「這張圖裡有什麼？它們在哪裡？」
輸出結果 整張圖片的分類標籤 (Labels) 多個物件的標籤 + 邊界框 (Bounding Boxes)
座標資訊 無 有（提供 [x, y, w, h] 座標）
適用場景 相簿自動分類、瑕疵品分類（良率檢測） 自駕車偵測行人、商店貨架商品盤點、保全監控

3. 人臉辨識 (Face)

  • 核心概念：提供人臉偵測、分析與識別能力。
  • 主要功能：
    • 人臉偵測 (Face Detection)：定位影像中的人臉，並提供人臉矩形 (Face Rectangle) 座標，還可識別臉部地標 (Face Landmarks，如眼睛、鼻子位置)。
    • 人臉驗證 (Face Verification, 1:1)：比對兩張人臉是否為同一個人。
    • 人臉識別 (Face Identification, 1:N)：在群組中尋找與特定人臉相似的人。
  • 考點（微軟負責任 AI 規範）：
    • 由於微軟的負責任 AI 原則（隱私權與安全性、公平性），人臉辨識（Face Verification/Identification）屬於限制存取（Limited Access）服務，開發人員必須提交申請並獲得核准後才能使用。
    • 人臉偵測中的敏感屬性（如情感識別、年齡推測、性別推測等）已預設停用，以防範潜在偏誤與隱私侵犯。

4. OCR（光學字元辨識）

  • 核心概念：偵測並擷取影像、PDF 或掃描文件中的印刷體或手寫文字。
  • 考點：
    • 層級結構：OCR 返回的資料具有層級關係：Pages（頁面） -> Paragraphs（段落） -> Lines（行） -> Words（字），每個層級都有對應的邊界多邊形 (Bounding Polygons)。
    • 工作負載分類：從掃描文件或圖片中讀取文字，底層是仰賴電腦視覺能力。在 Foundry 中，這常是資訊擷取（Information Extraction）解決方案的基礎。

5. 空間分析 (Spatial Analysis)

  • 核心概念：使用實時影片串流來理解人在特定物理空間中的行為與互動。
  • 主要功能：
    • 人數統計 (Person Counting)：統計特定區域內的人數。
    • 逗留時間偵測 (Person Loitering)：偵測人在區域內停留的時間是否超時。
    • 社交距離 (Physical Distancing)：偵測人與人之間的距離是否小於指定閾值。
    • 穿越線偵測 (Line Crossing)：偵測人何時跨越了設定好的虛擬線（例如：統計進入商店的人數）。
  • 考點：
    • 部署架構：空間分析處理的是高頻寬的即時視訊串流，出於延遲、隱私與網路頻寬考量，通常會部署在邊緣端 (Edge)。一般會使用帶有 GPU 的本地設備，配合 Azure IoT Edge 部署 Spatial Analysis 容器。

6. DALL-E 影像生成 (Image Generation)

  • 核心概念：根據使用者的自然語言描述 (Text-to-Image) 生成全新的、高質量的影像。
  • 呼叫參數與考點：
    • prompt：影像的文字描述，長度與細節直接影響生成品質。
    • n：生成的影像數量（DALL-E 3 目前在 Azure OpenAI 中僅支援 n=1）。
    • size：影像解析度，常用解析度為 1024x1024（正方形）、1024x1792（直式）、1792x1024（橫式）。
    • quality：生成品質，如 standard 或是 hd。
    • style：風格，如 vivid（鮮艷，預設）或 natural（自然）。
  • 2026年最新現況（ARF 絕對真實框架引用）：
    • 微軟已於 2026 年 3 月 4 日起淘汰 DALL-E 3，並升級為 gpt-image- 系列模型（例如 gpt-image-1、gpt-image-1.5、gpt-image-2）。
    • 新型的 gpt-image- 模型在 API 回傳時，通常預設回傳 base64 編碼的圖片資料字串 (b64_json)，而非以往 DALL-E 3 常用的公開 URL。這在開發應用程式時需要特別進行 base64 解碼處理。

二、 Python SDK 程式碼範例

1. 影像分析（影像分類與物件偵測）

以下範例使用最新 azure-ai-vision-imageanalysis 套件，展示如何連接 Azure AI Vision 服務並擷取影像分類標籤 (Tags) 與物件偵測資訊 (Objects)。

import os
from azure.ai.vision.imageanalysis import ImageAnalysisClient
from azure.ai.vision.imageanalysis.models import VisualFeatures
from azure.core.credentials import AzureKeyCredential

# 1. 配置端點與金鑰（可從環境變數讀取）
# 考點：呼叫服務前，必須在 Azure 佈建 Microsoft Foundry 或 Azure AI Vision 資源以取得端點與金鑰
endpoint = os.environ.get("VISION_ENDPOINT", "https://<your-resource-name>.cognitiveservices.azure.com/")
key = os.environ.get("VISION_KEY", "<your-key>")

# 2. 建立客戶端 (推薦在生產環境使用 with 語句，確保資源能正確釋放)
with ImageAnalysisClient(
    endpoint=endpoint,
    credential=AzureKeyCredential(key)
) as client:

    # 3. 指定待分析的影像 URL (亦可改用 analyze_from_image_data 輸入二進位檔案)
    image_url = "https://example.com/sample-image.jpg"

    # 4. 執行影像分析
    # 考點：在 visual_features 參數中指定所需要的特徵
    result = client.analyze_from_url(
        image_url=image_url,
        visual_features=[VisualFeatures.TAGS, VisualFeatures.OBJECTS],
    )

    # 5. 輸出影像分類結果 (Tags)
    print("=== [影像分類結果] ===")
    if result.tags is not None:
        for tag in result.tags.list:
            print(f"標籤: {tag.name:<15} 信賴度: {tag.confidence:.4f}")

    # 6. 輸出物件偵測結果 (Objects)
    print("\n=== [物件偵測結果] ===")
    if result.objects is not None:
        for obj in result.objects.list:
            # 物件的邊界框 (Bounding Box): x, y, width, height
            bbox = obj.bounding_box
            # 第一個 tag 通常是該物件最合適的類別名稱
            object_name = obj.tags[0].name
            confidence = obj.tags[0].confidence
            print(f"偵測到: {object_name:<12} 信賴度: {confidence:.4f} "
                  f"邊界框: [X:{bbox.x}, Y:{bbox.y}, W:{bbox.width}, H:{bbox.height}]")

elif hasattr(response.data[0], "b64_json") and response.data[0].b64_json:
    b64_data = response.data[0].b64_json
    print("影像生成成功！回傳格式為 base64 圖片資料字串。")

Question 10：多模態提示與 Playground 運作機制

  • 題目摘要：判斷多模態模型敘述是否正確。
    • 敘述 1：在 Foundry playground 中提示多模態模型時，可以上傳本機圖片並在同一則訊息中加入文字。 (是)
    • 敘述 2：使用 OpenAI Responses API 與支援視覺的模型時，圖片只能以 base64 編碼資料提供。 (否)
    • 敘述 3：包含圖片的提示需要部署純文字模型，因為多模態能力由應用程式層處理。 (否)
  • 答案：是、否、否
  • 結構化因果鏈分析： $$\text{多模態模型 (如 GPT-4o with Vision) 原生支援視覺與文字輸入} \longrightarrow \text{無需額外部署純文字模型} \longrightarrow \text{應用程式層僅負責傳遞資料，非處理多模態核心}$$ $$\text{OpenAI Responses API 接收多模態輸入} \longrightarrow \text{支援圖片 URL (如 Azure Blob SAS) 或 base64 編碼資料} \longrightarrow \text{「只能以 base64 傳遞」之敘述為偽}$$
  • 核心考點：多模態模型的原生的文字與圖像混合處理能力，以及 API 支援 URL 與 base64 雙重輸入格式。

Question 11：OpenAI Responses API 圖片編碼

  • 題目摘要：使用 OpenAI Responses API 與支援視覺的模型時，可以將圖片以何種方式提供給要求？
  • 答案：base64 編碼圖片資料字串 (base64-encoded image data)
  • 結構化因果鏈分析： $$\text{無公開 URL 之圖片資料（如本地圖片）} \longrightarrow \text{轉換為標準 Base64 字串} \longrightarrow \text{以 JSON 結構包裝傳入 API 要求} \longrightarrow \text{模型順利解析像素}$$
  • 核心考點：當圖片無法以公開 URL 存取時，必須將其編碼為 Base64 格式作為 API 的文字承載內容。

Question 20：文字識別的底層工作負載

  • 題目摘要：能偵測並讀取掃描文件與影像中文字的資訊擷取解決方案，仰賴何種 AI 技術？
  • 答案：電腦視覺 (computer vision)
  • 結構化因果鏈分析： $$\text{掃描文件/影像中的文字} \longrightarrow \text{本質上是圖像中的像素特徵} \longrightarrow \text{需先經過電腦視覺 (OCR) 進行邊緣與形狀偵測} \longrightarrow \text{辨識出字元並轉換為文字}$$
  • 核心考點：雖然此題與「資訊擷取」相關，但由於起點是「影像/掃描文件」，因此其最底層仰賴的 AI 工作負載是電腦視覺。

Question 31：多模態要求中的內容項目類型

  • 題目摘要：使用 Azure OpenAI Responses API 傳送圖片給支援視覺的模型進行分析，要求中應包含哪一種內容項目？
  • 答案：input_image
  • 結構化因果鏈分析： $$\text{Responses API 定義多模態要求的內容陣列} \longrightarrow \text{文字對應 }\texttt{"type": "input_text"}\text{，圖片對應 }\texttt{"type": "input_image"}$$
  • 核心考點：掌握 Responses API 規格中的內容項目類型。

Question 39：最快回應時間的訊息結構設計

  • 題目摘要：要傳送文字與圖片 URL 予視覺模型分析，如何設計訊息結構以確保最快回應時間？
  • 答案：使用者訊息在 content 陣列中同時包含文字項目與圖片項目。
  • 結構化因果鏈分析：
    • 拆分請求（錯誤路徑）： $$\text{文字要求 (Req 1) + 圖片要求 (Req 2)} \longrightarrow \text{兩次 HTTP 網路往返延遲} \longrightarrow \text{伺服器端需在記憶體中等待並拼接上下文} \longrightarrow \text{回應時間變慢}$$
    • 合併請求（正確路徑）： $$\text{單一要求中的 Content Array (文字 + 圖片)} \longrightarrow \text{單次 HTTP 網路往返延遲} \longrightarrow \text{模型一次性載入所有上下文進行推論} \longrightarrow \text{回應時間最快}$$
  • 核心考點：網路傳輸與 API 設計的最佳化。多模態模型支援在單次 User Message 的 content 陣列中傳遞複數個 input_text 和 input_image 項目。

Question 40：影像生成工作負載定義

  • 結構化因果鏈分析： $$\text{輸入：書面文字描述 (Prompt)} \longrightarrow \text{輸出：全新的產品圖片} \longrightarrow \text{Text-to-Image 生成模型 (如 DALL-E)} \longrightarrow \text{屬於「影像生成」工作負載}$$
  • 核心考點：區分不同的視覺工作負載。

Question 43：Python SDK 多模態完成程式碼

  • 題目摘要：開發應用程式在同一個要求中傳送文字與圖片，讓模型回傳文字答案，程式碼應如何完成？

  • 結構化因果鏈分析： $$\text{傳入：}\texttt{content: [{"type": "input_text", ...}, {"type": "input_image", ...}]} \longrightarrow \text{多模態模型處理} \longrightarrow \text{回傳文字解答} \longrightarrow \text{由屬性 }\texttt{response.output_text}\text{ 讀取}$$
  • 核心考點：與 Question 31 呼應，考驗多模態 SDK/API 呼叫的完整實作模式：輸入為 content 陣列（包含 input_text 與 input_image），文字輸出讀取為 output_text。

Question 47：視覺模型支援的圖片格式

  • 題目摘要：可用哪兩種格式將圖片提供給支援視覺的模型進行分析？
  • 答案：圖片的公開可存取 URL (a publicly accessible URL)；base64 編碼的圖片資料字串 (a base64 encoded image data string)
  • 結構化因果鏈分析：
    • 公開 URL 鏈： $$\text{提供圖片網址} \longrightarrow \text{雲端服務透過 HTTP(S) 直接下載影像資料} \longrightarrow \text{傳送給模型分析}$$
    • Base64 鏈： $$\text{本地圖片轉為 base64 字串} \longrightarrow \text{將編碼資料直接嵌入要求承載中} \longrightarrow \text{傳送給模型分析}$$
  • 核心考點：多模態模型接收影像的兩種標準管道。

2. Azure AI Speech 核心服務與考點分析

Azure AI Speech 提供了語音與文字雙向轉換及處理的能力。考試側重於「即時 vs 批次」的選擇、SDK 連線設定、語音合成的輸出控制以及 Voice Live 的架構。

核心功能拆解

  1. 語音轉文字 (Speech-to-Text, STT)
  2. 即時轉錄 (Real-time Transcription)：適用於麥克風即時輸入、語音助理、即時會議字幕。
  3. 批次轉錄 (Batch Transcription)：適用於已儲存的大量音訊檔案（如存放在 Azure Blob Storage 內的數千通客服錄音）。採用非同步 API 處理。
  4. 文字轉語音 (Text-to-Speech, TTS)
  5. 將文字合成自然流暢的口語音訊。
  6. 語音合成標記語言 (SSML)：XML 格式，用於精細調整發音、語速、音調、停頓、音量及情感語氣。
  7. 語音翻譯 (Speech Translation)
  8. 在單次呼叫中同時完成語音識別與多語言翻譯，支援語音到文字及語音到語音（翻譯後再合成）。
  9. 說話者辨識 (Speaker Recognition)
  10. 說話者驗證 (Verification, 1:1)：確認說話者是否為其聲稱的身分（聲紋雙重驗證）。
  11. 說話者識別 (Identification, 1:N)：在已知說話者群組中，辨識出當前說話者是誰。
  12. 即時雙向語音推理 (Voice Live)
  13. 將語音轉文字 (STT)、語言模型推理與文字轉語音 (TTS) 整合成單一低延遲的即時語音對話管道，適合開發高互動性的語音 Agent。

為滿足 AI-901 中關於程式碼實作的考點，以下提供文字翻譯、TTS 語音合成及 STT 語音辨識的核心 Python 程式碼。

3.1 文字翻譯 (Text Translation)

此處展示呼叫 Azure AI Translator REST API 的標準實作，這也是考試與實務中最通用的方式。

import requests
import uuid

def translate_text(text_to_translate: str, target_language: str = "zh-Hant") -> str:
    # 設定端點與金鑰（請替換為您在 Azure 部署的實際資訊）
    subscription_key = "YOUR_TRANSLATOR_KEY"
    endpoint = "https://api.cognitive.microsofttranslator.com"
    path = '/translate'
    constructed_url = endpoint + path

    params = {
        'api-version': '3.0',
        'to': target_language
    }

    headers = {
        'Ocp-Apim-Subscription-Key': subscription_key,
        'Ocp-Apim-Subscription-Region': "YOUR_RESOURCE_REGION",  # 例如: eastus
        'Content-type': 'application/json',
        'X-ClientTraceId': str(uuid.uuid4())
    }

    body = [{
        'text': text_to_translate
    }]

    response = requests.post(constructed_url, params=params, headers=headers, json=body)
    response.raise_for_status()
    results = response.json()

    # 傳回翻譯後的文字
    return results[0]['translations'][0]['text']

# 測試呼叫
if __name__ == "__main__":
    translated = translate_text("Hello, welcome to Azure AI Foundry!", "zh-Hant")
    print(f"翻譯結果: {translated}")

3.2 文字轉語音 (TTS) 語音合成並儲存至檔案

此程式碼精確對應了考題中要求將合成語音存檔的 SDK 寫法。

import azure.cognitiveservices.speech as speechsdk

def text_to_speech_file(text: str, output_filename: str = "output.wav"):
    # 1. 使用 SpeechConfig 設定連線 (金鑰與區域)
    # [考點] SpeechConfig 負責設定訂用帳戶金鑰與區域以建立服務連線
    speech_config = speechsdk.SpeechConfig(
        subscription="YOUR_SPEECH_KEY", 
        region="YOUR_SPEECH_REGION"
    )

    # 設定合成語音的語言與說話者 (可選)
    speech_config.speech_synthesis_voice_name = "zh-TW-HsiaoChenNeural"

    # 2. 設定 AudioOutputConfig 來指定輸出目的地為檔案
    # [考點] 必須使用 AudioOutputConfig(filename=...) 才能將音訊直接寫入檔案
    audio_config = speechsdk.audio.AudioOutputConfig(filename=output_filename)

    # 3. 初始化 SpeechSynthesizer
    synthesizer = speechsdk.SpeechSynthesizer(
        speech_config=speech_config, 
        audio_config=audio_config
    )

    # 4. 執行非同步合成並等待其完成
    result = synthesizer.speak_text_async(text).get()

    # 5. 檢查合成結果
    if result.reason == speechsdk.ResultReason.SynthesizingAudioCompleted:
        print(f"成功將文字合成語音並儲存至: {output_filename}")
    elif result.reason == speechsdk.ResultReason.Canceled:
        cancellation_details = result.cancellation_details
        print(f"語音合成取消: {cancellation_details.reason}")
        if cancellation_details.error_details:
            print(f"錯誤詳情: {cancellation_details.error_details}")

# 測試呼召
if __name__ == "__main__":
    text_to_speech_file("您好，歡迎使用微軟語音合成服務！", "notifications.wav")

3.3 語音轉文字 (STT) 單次語音辨識

此程式碼精確對應了聆聽語音命令並轉換成文字的一次性辨識 SDK 寫法。

import azure.cognitiveservices.speech as speechsdk

def recognize_speech_once():
    # 1. 初始化 SpeechConfig
    speech_config = speechsdk.SpeechConfig(
        subscription="YOUR_SPEECH_KEY", 
        region="YOUR_SPEECH_REGION"
    )
    speech_config.speech_recognition_language = "zh-TW"

    # 2. 設定音訊輸入 (預設為系統麥克風)
    audio_config = speechsdk.audio.AudioConfig(use_default_microphone=True)

    # 3. 建立 SpeechRecognizer
    recognizer = speechsdk.SpeechRecognizer(
        speech_config=speech_config, 
        audio_config=audio_config
    )

    print("請開始說話（聆聽語音命令中...）...")

    # 4. 執行一次性辨識
    # [考點] recognize_once() 會聆聽單一發言，並在偵測到停頓後停止辨識並傳回文字
    result = recognizer.recognize_once()

    # 5. 處理辨識結果
    if result.reason == speechsdk.ResultReason.RecognizedSpeech:
        print(f"辨識結果: {result.text}")
        return result.text
    elif result.reason == speechsdk.ResultReason.NoMatch:
        print("未偵測到相符的語音。")
    elif result.reason == speechsdk.ResultReason.Canceled:
        cancellation_details = result.cancellation_details
        print(f"辨識已取消: {cancellation_details.reason}")
        if cancellation_details.error_details:
            print(f"錯誤詳情: {cancellation_details.error_details}")
    return None

# 測試呼叫
if __name__ == "__main__":
    recognize_speech_once()

    • 干擾項分析：
    • AudioConfig：用來設定音訊輸入/輸出源（麥克風、揚聲器、音訊檔）。

Question 13：將合成音訊儲存至檔案

  • 考點解析：
    • 考驗對新一代即時語音推理架構 Voice Live 定位的認識。它是一套端到端的對話流，大大降低了構建低延遲語音助理的複雜度。

  • 考點解析：

    • 干擾項分析：
    • speak_text_async()：這是語音合成的 API，方向相反。
    • start_continuous_recognition()：用於長篇演講、會議記錄等需要持續辨識並觸發事件的情境。

  • 正確答案：speech to text batch transcription（語音轉文字批次轉錄）
  • 考點解析：
    • 當音訊檔案是「既有的、大容量的、存放在儲存體中」，應採用批次轉錄 (Batch Transcription)。這是一個非同步作業，可同時處理多個大檔案並提供較高的輸送量。
    • 干擾項分析：
    • real-time transcription：適用於即時串流，對儲存中的歷史檔案不符效益且實作複雜。

Question 27：識別文字中的實體 (NER)

  • 題目情境：自動識別客服電子郵件中提到的人員（people）、組織（organizations）與地點（locations）。你應該使用哪一種文字分析技術？
  • 正確答案：Named Entity Recognition (NER)（命名實體辨識）
  • 考點解析：
    • 這是 Azure AI Language 的基礎 NLP 能力。只要題目要求對文字中的特定專有名詞進行分類（如人、事、時、地、物），對應技術即為 NER。

    • sentiment analysis：評估情緒正負面。
    • key phrase extraction：擷取重要字彙，但無法對這些字彙進行「人員/組織/地點」的語意分類。
    • summarization：將長文縮短。

第一部分：核心概念詳解 (Foundry Core Concepts)

在 Microsoft AI Foundry 生態系中，實作生成式 AI 應用主要圍繞在四大技術支柱：檢索增強生成 (RAG)、提示工程 (Prompt Engineering)、提示流 (Prompt Flow) 以及 AI 代理 (Agents)。

1.1 RAG (Retrieval-Augmented Generation, 檢索增強生成)

RAG 是一種結合「資訊檢索」與「文本生成」的混合架構。大型語言模型（LLM）的知識受限於其訓練截止日，且容易產生「幻覺」（Hallucination）。RAG 透過在推論階段動態將外部私有或即時知識庫的內容注入提示詞中，使模型能生成精確且有事實根據的回應。

在 Azure AI Foundry 中的實作步驟

  1. 建立資料連接 (Data Connections)：連接外部資料來源，例如 Azure Blob Storage、OneLake 或本地檔案。
  2. 資料前處理與分塊 (Chunking)：將長文件切分為固定大小的區塊（例如 512 tokens），並設定重疊區（Overlap）以保持上下文連貫。
  3. 向量化 (Vectorization/Embedding)：調用 Embedding 模型（如 text-embedding-3-small）將文本區塊轉換為多維向量。
  4. 建立向量索引 (Vector Index)：將向量存入 Azure AI Search，這是微軟推薦的向量資料庫解決方案。
  5. 檢索與混合搜尋 (Hybrid Search)：在查詢時，結合關鍵字搜尋 (BM25) 與向量搜尋，並透過重排序 (Semantic Ranker) 篩選出最相關的 Context。

1.2 Prompt Engineering (提示工程)

提示工程 is 透過設計、優化輸入給模型的文本，以引導模型輸出預期結果的過程。

核心設計原則

  • 明確性 (Specificity)：清楚說明任務目標，避免模糊字眼。
  • 結構化提示詞：使用 XML 標籤（如 <context>、<instructions>）來分隔提示詞的不同部分。
  • Few-shot Learning (少樣本學習)：在提示中提供 1 到 3 個「輸入-輸出對」的範例，引導模型學習特定輸出格式或邏輯。
  • System Message/Instructions vs User Message：
  • System Message：定義模型的「系統角色（Role）」、「行為約束（Constraints）」與「基本規則」，模型在整個對話生命週期中皆會嚴格遵守。
  • User Message：使用者當下輸入的具體指令或問題。

關鍵推論參數調校

  • Temperature (溫度)：控制生成的隨機性。數值介於 0 與 2 之間。
  • 0.0：結果高度確定、一致，適合程式碼生成、事實型問答。
  • 0.7 - 1.0：結果多樣且具創意，適合腦力激盪、寫作。
  • Top P (核取樣)：與 Temperature 類似，但它是控制模型考慮機率累計前 P% 的 token 集合。通常建議僅調整 Temperature 或 Top P 其中之一，而非同時調整。
  • Max Tokens / Max Completion Tokens：限制模型單次輸出的最大 Token 數量。這不是用來取代安全性或品質評估的，而是用於硬性的資源限制與成本控制。

1.3 Prompt Flow (提示流)

Prompt Flow 是微軟開發的開發者工具，用於編排、測試與評估基於 LLM 的應用程式。它將應用程式抽象化為有向無環圖 (DAG, Directed Acyclic Graph)，其中節點（Nodes）可以是 LLM、Python 程式碼或資料處理工具。

三種 Flow 類型

  1. Standard Flow (標準流)：適用於通用的批次處理或無狀態應用（如文件摘要、自動翻譯）。
  2. Chat Flow (對談流)：專為聊天機器人設計，原生支援對話歷史記錄（Chat History）與會話狀態管理。
  3. Evaluation Flow (評估流)：特殊的流，以 Standard/Chat Flow 的輸出作為輸入，計算品質與安全性指標。

評估與批次測試 (Evaluation & Batch Run)

  • Groundedness (真實性/立論依據)：評估模型產出的回應是否「完全基於」檢索到的 Context，檢測是否有幻覺。
  • Relevance (相關性)：回應是否切合使用者的提問。
  • Fluency / Coherence (流暢度/一致性)：語言品質與邏輯結構。
  • Safety / Content Filters (安全性/內容過濾)：檢測是否包含仇恨言論、自殘、性暗示或暴力內容。

  • [!IMPORTANT] 評估器 (Evaluators) 的定位是量測與監控。當評估器偵測到模型輸出品質不佳時，它不會也不可能自動重新訓練模型，亦無法取代 Token 限制設定。修正品質問題的正確途徑是：修改 Prompt、調整系統指示、變更檢索策略或對模型進行微調 (Fine-tuning)。

1.4 Playground (遊樂場) 的使用

Playground 是 Azure AI Foundry Portal 提供的 Web UI 工具，主要用於快速原型設計與實驗： - 模式選擇：支援 Chat（對話模式）、Completions（單次補全）與 Agents / Assistants（代理模式）。 - 即時調整：可在介面中直接更換模型部署、修改 System Message、調整 Parameters (Temperature, Max Tokens) 並測試效果。 - Add your data (RAG 整合測試)：可以在不寫任何程式碼的情況下，一鍵連結 Azure AI Search 索引，在 Web UI 上測試 RAG 的檢索效果。 - View Code (檢視程式碼)：一旦在 Playground 調整出滿意的參數與 System Message，可點擊「View Code」導出適用於 Python、C# 或 curl 的程式碼，直接轉移至開發環境。

AI Agent 是一種能利用 LLM 的推理能力，自動規劃步驟、使用工具 (Tools) 並與環境互動以達成複雜目標的實體。

  • Code Interpreter (程式碼解譯器)：在隔離的安全沙箱中執行 Python 程式碼，適合處理複雜數學計算、數據分析與圖表繪製。
  • Bing Search (微軟搜尋)：允許 Agent 搜尋網頁以獲取即時的外部資訊。
  • Azure AI Search (RAG)：整合向量搜尋，讓 Agent 讀取私有企業知識庫。
  • Function Tooling / Custom Tools (自訂工具/函式呼叫)：
  • 開發者定義本地 Python 函數，將其綱要 (Schema) 註冊給 Agent。
  • 當 Agent 判斷需要此工具時，會暫停執行並要求 Client 執行該函數（requires_action 狀態），Client 執行完畢後將結果提交回 Run，Agent 再繼續完成任務。

2.1 Azure AI Inference SDK - 呼召 Chat Completions 與 System Prompt 配置

此範例展示如何使用 azure-ai-inference SDK 來呼叫部署好的 LLM，配置系統提示詞以設定模型行為與參數。

import os
from azure.ai.inference import ChatCompletionsClient
from azure.ai.inference.models import SystemMessage, UserMessage
from azure.identity import DefaultAzureCredential

def run_chat_completion():
    # 1. 取得 Azure AI Foundry 專案的 Endpoint 與認證
    endpoint = os.environ.get("AZURE_AI_INFERENCE_ENDPOINT", "https://your-endpoint.services.ai.azure.com")
    credential = DefaultAzureCredential()

    # 2. 建立 ChatCompletionsClient
    client = ChatCompletionsClient(
        endpoint=endpoint,
        credential=credential
    )

    # 3. 設計系統提示 (System Message) 與使用者提示 (User Message)
    messages = [
        SystemMessage(content=(
            "你是一位專業的金融投資分析師。請一律使用繁體中文（台灣用語）回答問題。\n"
            "在回答時，請遵守以下限制：\n"
            "1. 僅根據確切的事實或專業知識庫作答，若不確定請坦白告知。\n"
            "2. 結構化條列回覆，並在最後提供警語：『投資有風險，申購前應詳閱公開說明書』。"
        )),
        UserMessage(content="請分析定期定額投資大盤 ETF 的主要優缺點。")
    ]

    # 4. 呼叫服務並配置推論參數
    print("正在發送請求至 Azure AI Foundry...")
    response = client.complete(
        messages=messages,
        model="gpt-4o",  # 指定已部署模型的 Friendly Name
        temperature=0.3,  # 調低隨機性以獲取穩定的分析報告
        max_tokens=1000   # 限制最大輸出長度
    )

    # 5. 輸出生成的回應
    print("\n--- 模型生成回應 ---")
    print(response.choices[0].message.content)

if __name__ == "__main__":
    run_chat_completion()

2.2 Azure AI Projects SDK - 實作 AI Agent 與 Tool Calling / Function Calling

此範例展示如何使用 azure-ai-projects SDK 建立具備自訂工具 (Function Tool) 的 AI Agent。此範例涵蓋了：定義本地 Tool、將 Tool 註冊給 Agent、建立對話 Thread、啟動 Run、以及處理 requires_action 狀態以執行本地函數並回復結果的完整 Run Loop 機制。

import os
import json
import time
from azure.ai.projects import AIProjectClient
from azure.ai.projects.models import FunctionTool, ToolSet, RunStatus
from azure.identity import DefaultAzureCredential

# ==========================================
# 1. 定義本地自訂工具 (Function Tool)
# ==========================================
def get_stock_price(ticker: str) -> str:
    """
    獲取指定股票代號的最新股價資訊。

    :param ticker: 股票代號，例如 AAPL, TSLA, 2330
    :return: 包含股價與日期的 JSON 字串
    """
    ticker_upper = ticker.upper()
    if "2330" in ticker_upper or "TSMC" in ticker_upper:
        price = "1020 TWD"
    elif "AAPL" in ticker_upper:
        price = "190 USD"
    else:
        price = "未知代號，無法獲取股價"

    return json.dumps({"ticker": ticker_upper, "price": price, "status": "SUCCESS", "last_updated": "2026-06-30"})

def run_agent_with_tool_calling():
    # 2. 建立 AI Project Client
    connection_string = os.environ.get("AZURE_AI_PROJECTS_CONNECTION_STRING", "eastus2.api.azure.com;...")
    project_client = AIProjectClient.from_connection_string(
        conn_str=connection_string,
        credential=DefaultAzureCredential()
    )

    # 3. 封裝自訂工具並建立 ToolSet
    stock_tool = FunctionTool(
        name="get_stock_price",
        description="查詢特定股票代號的最新市場交易價格。",
        func=get_stock_price
    )

    tool_set = ToolSet()
    tool_set.add_tool(stock_tool)

    # 4. 建立 Agent 實體，設定系統指示與工具集
    print("正在建立 Agent...")
    agent = project_client.agents.create_agent(
        model="gpt-4o",
        name="finance-agent",
        instructions="你是一位金融助理，當使用者詢問股價時，你必須使用 get_stock_price 工具查詢，並為使用者進行解說。",
        toolset=tool_set
    )
    print(f"Agent 建立成功，ID: {agent.id}")

    # 5. 建立對話 Thread 與 Message
    thread = project_client.agents.create_thread()
    message = project_client.agents.create_message(
        thread_id=thread.id,
        role="user",
        content="請問現在台積電 (2330) 的股價是多少？"
    )

    # 6. 啟動 Run (執行)
    run = project_client.agents.create_run(
        thread_id=thread.id,
        agent_id=agent.id,
        tool_choice="auto" 
    )
    print(f"Run 已啟動，ID: {run.id}，目前狀態: {run.status}")

    # 7. Run Loop: 監控狀態並處理工具調用 (Requires Action)
    while True:
        run = project_client.agents.get_run(thread_id=thread.id, run_id=run.id)

        if run.status == RunStatus.COMPLETED:
            print("執行完成！")
            break

        elif run.status == RunStatus.FAILED:
            print(f"執行失敗: {run.last_error}")
            break

        elif run.status == RunStatus.REQUIRES_ACTION:
            print("Agent 決定調用工具，進入 REQUIRES_ACTION 狀態...")

            tool_calls = run.required_action.submit_tool_outputs.tool_calls
            tool_outputs = []

            for tool_call in tool_calls:
                function_name = tool_call.function.name
                arguments = json.loads(tool_call.function.arguments)
                print(f" -> 請求呼叫函數: {function_name}，參數: {arguments}")

                if function_name == "get_stock_price":
                    output_data = get_stock_price(ticker=arguments.get("ticker"))
                    tool_outputs.append({
                        "tool_call_id": tool_call.id,
                        "output": output_data
                    })

            print("正在提交工具輸出結果...")
            run = project_client.agents.submit_tool_outputs_to_run(
                thread_id=thread.id,
                run_id=run.id,
                tool_outputs=tool_outputs
            )

        else:
            time.sleep(1)

    # 8. 取得並顯示對話結果
    messages = project_client.agents.list_messages(thread_id=thread.id)
    print("\n--- 對話歷程紀錄 ---")
    for msg in reversed(messages.data):
        content_text = "".join([part.text.value for part in msg.content if hasattr(part, 'text')])
        print(f"[{msg.role.upper()}]: {content_text}")

    # 9. 清理資源
    project_client.agents.delete_agent(agent.id)
    print("資源清理完畢。")

if __name__ == "__main__":
    run_agent_with_tool_calling()

3.2 關鍵考點深度剖析與易錯陷阱

1. 代理工具調用控制 (tool_choice)

  • 核心概念：
  • none：強制不使用任何工具。模型只會產生純文字回應。
  • auto：模型自行評估。根據使用者的輸入與上下文，若有需要才呼叫註冊的工具；不需要則直接回答。
  • required：強制模型必須呼叫至少一個工具。
  • 考生易錯點 (Trap)：
  • 容易將 none 誤解為「模型自行決定是否呼叫工具（即誤與 auto 混淆）」。
  • 題目中如果出現 「一律 / 總是 (Always)」 呼叫工具的需求，答案必須選 required。選 auto 雖然有可能會呼叫，但無法「保證一律呼叫」。

2. 評估器 (Evaluators) 的能力邊界

  • 核心概念：評估器是設計用來量化模型輸出品質（流暢度、相關性、真實性）與安全性（敏感內容過濾）的輔助工具。
  • 考生易錯點 (Trap)：
  • 誤以為評估器可以「自動閉環重新訓練模型」：微軟目前沒有提供在評估出品質下降時「自動啟動 Fine-tuning Job」的原生機制。
  • 誤以為評估器可以取代「權杖限制 (Token Limit)」：Token 限制（如 Max Completion Tokens、TPM）是 API 請求層級的資源配額控制，評估器無法動態干涉或取代此設定。

3. 系統指示 (System Prompt / Instructions) 的功能與區分

  • 核心概念：引導模型扮演特定角色（例如金融分析師）、遵守特定回應格式（例如 JSON 或 Markdown）與限制條件（例如「請勿回答醫療建議」）。
  • 考生易錯點 (Trap)：
  • 題目常會混淆「控制模型角色/行為的設定」與「限制硬體/配額的參數」：
    • 角色與行為 $\rightarrow$ 設定 System Instructions / System Prompt。
    • 隨機性 $\rightarrow$ 設定 Temperature / Top P。
    • 輸出長度 $\rightarrow$ 設定 Max Completion Tokens。
    • 推論區域與 TPM 配額 $\rightarrow$ 這是 Azure 資源部署設定，與 Prompt 毫無關係。

4. Model Catalog 的定位

  • 核心概念：Model Catalog 是 Azure AI Foundry 的模型大本營，支援比較（透過基準測試指標 Benchmark metrics）與一鍵部署。
  • 考生易錯點 (Trap)：
  • 不要與 Prompt Flow（編排工具）或 Playground（動態測試 UI）混淆。題幹中凡是提到「比較 (Comparing) 與部署 (Deploying) 多樣化模型」，答案必定是 Model catalog。

一、 Azure AI Document Intelligence 模型類型深研

Azure AI Document Intelligence (前稱為 Form Recognizer) 是一項基於機器學習的服務，可從文件中擷取文字、金鑰/值對、表格和結構化資料。在設計與實作時，必須根據文件格式的變異程度與業務需求，選擇合適的模型類型：

1. 預建模型 (Prebuilt Models)

  • 功能與特色：微軟使用大量代表性資料預先訓練好的模型。可直接辨識並擷取特定常見文件類型中的關鍵欄位，無須自行標記或訓練。
  • 適用情境：
    • 發票分析：prebuilt-invoice（擷取供應商、日期、總金額、品項等）。
    • 收據分析：prebuilt-receipt（擷取商家名稱、交易時間、稅金、總計等）。
    • 身分證明文件：prebuilt-idDocument（護照、駕照等）。
    • 商務名片：prebuilt-businessCard。
    • 稅務表單：如 prebuilt-w2（美國稅單）。
  • 訓練與部署流程：無需訓練與部署，直接透過 API 呼叫端點，指定 modelId 即可立即使用。

2. 自訂擷取模型 (Custom Extraction Models)

當文件格式不在預建模型支援範圍內時，需自行標記訓練。自訂擷取模型分為兩大技術路線：

A. 自訂範本模型 (Custom Template Models)

  • 功能與特色：基於文件視覺版面配置與幾何結構。模型會學習文件上各欄位所在的固定物理位置。
  • 適用情境：結構高度固定、格式一致的文件。例如同一個合作夥伴所設計的固定格式表單、訂購單。
  • 資料需求：極少，最少僅需要 5 張 格式相同的範本文件。
  • 訓練與部署流程：
    1. 收集至少 5 張相同格式的範本文件。
    2. 將文件上傳至 Azure Blob 儲存體，並設定 CORS 存取權。
    3. 使用 Document Intelligence Studio 建立「Custom extraction model - Template」專案。
    4. 標記 (Label) 欲擷取的欄位（定義 Key-Value 對、表格等）。
    5. 點選 Train，選擇 template 訓練類型，取得 Model ID 後即可呼叫。

B. 自訂類神經模型 (Custom Neural Models)

  • 功能與特色：結合深度學習與大型語言模型技術，能理解文件中的語意與上下文，而非單純依賴版面幾何位置。
  • 適用情境：半結構化或非結構化文件，格式變異度高，但資訊語意相似。例如不同公司撰寫的合約、同意書、出貨單等。
  • 資料需求：建議至少 5 到 10 張 起步，包含不同版面配置的樣本。
  • 訓練與部署流程：
    1. 收集涵蓋不同版面的相似主題文件。
    2. 上傳至 Blob 儲存體並在 Studio 中建立「Custom extraction model - Neural」專案。
    3. 跨多種版面標記相同的邏輯欄位（例如：合約生效日期、甲方名稱）。
    4. 點選 Train，選擇 neural 訓練類型（訓練時間較 template 長，但泛化效果極佳）。

3. 自訂分類模型 (Custom Classification Models)

  • 功能與特色：這類模型不負責擷取欄位，而是負責將輸入的文件分類為已定義好的類型，並支援多文件檔案分割 (Splitting)。
  • 適用情境：當輸入是混合了多種文件的單一 PDF（例如一個 PDF 內含 1 張發票、1 張合約、1 張駕照），需要先自動辨識類型並拆分成獨立文件。
  • 訓練與部署流程：
    1. 為每個類別準備至少 5 個 範本（例如 5 張發票、5 份合約）。
    2. 在 Studio 建立「Custom classification model」專案，將樣本指派給對應的類別標籤 (Class)。
    3. 訓練後取得 Classifier ID。在分析管道中，可先呼叫此分類器，識別出文件類別後再將分割後的文件送往對應的自訂擷取模型處理。

二、 Azure Content Understanding (Foundry 整合方案)

在 Azure AI Foundry (以前的 Azure AI Studio) 中，微軟推出了 Azure Content Understanding 服務。這項服務是將文件、影像、音訊和影片分析整合在一個統一的分析器架構下。

1. 核心觀念

  • 非同步分析 (Asynchronous Analysis)：因為多模態資料處理與欄位結構化對應屬於長時間執行作業 (LRO)，Content Understanding 採用非同步架構。呼叫時會立即回傳作業 Poller，應用程式需輪詢直到結果完成。
  • 結構描述 (Schema)：由使用者定義要從非結構化內容中擷取哪些結構化欄位（例如欄位名稱、資料型別、巢狀物件或陣列），分析器會依此 Schema 輸出格式化的 JSON。
  • 分析器類型：
    • 文件分析器 (Document Analyzer)：處理 PDF、Word 或掃描圖檔，擷取文件中的文字與定義好的 Schema 欄位。
    • 音訊分析器 (Audio Analyzer)：處理 WAV、MP3 等音訊，自動進行語音轉寫/轉錄 (Transcription) 並根據 Schema 提取資訊（例如客服錄音的客怨原因）。
    • 影像分析器 (Image Analyzer)：處理相片，擷取視覺特徵或 Schema 指定的標籤。
    • 影片分析器 (Video Analyzer)：處理影音檔案，擷取時序事件、語音逐字稿與畫面特徵。

1. 使用 azure-ai-documentintelligence (最新 v1.0 SDK) 分析發票

此 SDK 專用於 Azure AI Document Intelligence，展示如何使用預建發票模型 (prebuilt-invoice) 擷取欄位：

import os
from azure.core.credentials import AzureKeyCredential
# 導入最新版 Document Intelligence 用戶端與模型類別
from azure.ai.documentintelligence import DocumentIntelligenceClient
from azure.ai.documentintelligence.models import AnalyzeDocumentRequest

def analyze_invoice_v1(file_path: str):
    endpoint = os.environ.get("AZURE_DOCUMENT_INTELLIGENCE_ENDPOINT", "https://your-resource.cognitiveservices.azure.com/")
    key = os.environ.get("AZURE_DOCUMENT_INTELLIGENCE_KEY", "your-key")

    # 1. 建立 Client
    client = DocumentIntelligenceClient(endpoint=endpoint, credential=AzureKeyCredential(key))

    # 2. 以二進位方式讀取本地發票 PDF
    with open(file_path, "rb") as f:
        # 3. 呼叫非同步分析方法 (LRO)，指定使用 prebuilt-invoice 模型
        poller = client.begin_analyze_document(
            model_id="prebuilt-invoice",
            analyze_request=f,
            content_type="application/pdf"
        )

    # 4. 等待分析完成並取回 AnalyzeResult 結果
    result = poller.result()

    # 5. 剖析並輸出結構化欄位
    if result.documents:
        for doc in result.documents:
            print(f"--- 辨識出文件類型: {doc.doc_type} (信心度: {doc.confidence}) ---")
            fields = doc.fields

            # 擷取供應商名稱 (VendorName)
            vendor = fields.get("VendorName")
            if vendor:
                print(f"供應商名稱: {vendor.get('valueString')} (信心度: {vendor.get('confidence')})")

            # 擷取發票日期 (InvoiceDate)
            inv_date = fields.get("InvoiceDate")
            if inv_date:
                print(f"發票日期: {inv_date.get('valueDate')} (信心度: {inv_date.get('confidence')})")

            # 擷取發票總金額 (InvoiceTotal)
            total = fields.get("InvoiceTotal")
            if total:
                # 總金額通常為貨幣型別，內含金額與貨幣代碼
                currency_val = total.get("valueCurrency", {})
                amount = currency_val.get("amount")
                currency = currency_val.get("code", "USD")
                print(f"發票總金額: {amount} {currency} (信心度: {total.get('confidence')})")
