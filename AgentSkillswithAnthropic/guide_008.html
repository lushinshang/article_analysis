核心概念

SKILL.md 檔案結構

一個 Skill 檔案有兩個主要部分：

  1. YAML Frontmatter：頂部的元資料
  2. Body Content：下方的 Markdown 指令

Frontmatter 必填欄位

欄位限制
name最多 64 字元；僅小寫字母、數字、連字號；不能以連字號開頭或結尾；必須與父目錄同名；建議用「動詞+ing」形式
description最多 1024 字元；描述 Skill「做什麼」和「何時使用」；包含觸發關鍵字

Frontmatter 選用欄位

欄位說明
license授權名稱或授權檔參考
compatibility環境需求（最多 500 字元）
metadata任意鍵值對（如 author、version）
allowed-tools預核准工具清單（實驗性功能）

Body Content 最佳實踐

建議結構

  • 步驟化指令（Step-by-step Instructions）
  • 輸入格式 / 輸出格式 / 範例
  • 常見邊界案例（Edge Cases）
  • 保持在 500 行以內
  • 詳細參考資料移到獨立檔案
  • 參考保持一層深度（避免巢狀引用）
  • 路徑一律使用正斜線（/），即使在 Windows 上

自由度設計

自由度描述適用場景
高自由度一般性文字指引，多種做法皆可創意輸出、風格選擇
中自由度提供範例程式碼/模式，但允許變化資料分析、報告格式
低自由度指定特定腳本，必須依序執行合規流程、測試流程

選用目錄

目錄用途注意事項
/assets範本、圖片、schema、查找表僅在需要時載入
/references額外文件，代理視需要讀取超過 100 行的檔案建議加入目錄（TOC）
/scripts可執行的程式碼需明確文件化依賴；說明是「執行」還是「閱讀」

Skill 評估方法

用 Skill Creator 檢查最佳實踐

在 Claude Code 中安裝 skill-creator，用子代理平行評估多個 Skills：

# 安裝 Anthropic Skills marketplace
# Settings > Marketplace > anthropic/skills

# 要求評估
"Use the skill-creator to evaluate how my skills follow best practices.
 Launch subagents in parallel for each skill."

單元測試框架

{
  "skills": ["generating-practice-questions"],
  "queries": [
    "Generate questions and save to output.md",
    "Generate questions and save to output.tex"
  ],
  "files": ["test-files/notes.pdf", "test-files/notes.tex"],
  "expected_behavior": [
    "Successfully reads and extracts the input file",
    "Extracts all learning objectives",
    "Generates the 4 types of questions",
    "Follows the guidelines for each question",
    "Uses the correct output templates",
    "LaTeX output successfully compiles",
    "Saves to correct output file"
  ]
}

學習路徑

兩個範例 Skill 深度剖析

Skill 1：generating-practice-questions

  • 用途：從講義產生練習題
  • 亮點：
    • 支援多種輸入格式（PDF、LaTeX、Markdown）
    • 4 種題型（True/False、解釋題、程式題、應用題）
    • 輸出範本放在 assets/（按需載入 LaTeX 或 Markdown 範本）
    • 外部參考放在 references/
  • 評分：9/10（可改善精簡度）

Skill 2：analyzing-time-series

  • 用途：分析 CSV 時間序列資料的特性
  • 亮點：
    • 三個 Python 腳本：visualize.py、diagnose.py、decomposition.py
    • 低自由度設計：明確指定腳本執行順序
    • 明確的輸出目錄結構
    • 依賴清單明確列出
  • 評分：10/10

評估驅動開發（EDD）

課程建議的 Skill 開發流程：

  1. 設計：定義輸入/輸出/步驟
  2. 實作：撰寫 SKILL.md + 相關檔案
  3. 靜態檢查：用 Skill Creator 評估最佳實踐
  4. 動態測試：用單元測試框架驗證行為
  5. 人工回饋：收集真實使用者的回饋
  6. 跨模型測試：在所有目標模型上測試

資安 Skill 設計範例

建立一個「事件回應 Skill」：低自由度設計，明確指定 NIST SP 800-61 的步驟順序（準備 → 偵測 → 遏制 → 根除 → 復原 → 善後）。每個步驟引用獨立的參考文件。用單元測試確認每個步驟都不會被跳過。

常見誤區

誤區：不區分「執行」和「閱讀」腳本

在 SKILL.md 中引用腳本時，必須明確說明是要 Claude 「執行這個腳本」還是「閱讀這個腳本作為參考」。模糊的引用會導致非預期的行為。

誤區：不列出腳本依賴

如果你的 scripts/ 目錄中的 Python 腳本依賴特定套件（如 pandas、matplotlib），必須在 Skill 中明確列出並指示安裝方式。否則在某些環境中腳本會執行失敗。

誤區：只在一個模型上測試

不同模型對 Skill 指令的遵從程度不同。課程明確建議在所有你計劃使用的模型上測試 Skill。

延伸思考

Skill 的品質指標

如何量化一個 Skill 的品質？可以考慮：

  • 可預測性：相同輸入下，多次執行的輸出一致性
  • 正確性：輸出是否符合 expected_behavior
  • 效率：消耗的 token 數量
  • 可維護性：修改一個步驟需要改動多少檔案

思考題

  1. 高自由度 vs. 低自由度 Skill 各適合什麼場景？在你的工作中，哪些流程需要低自由度（嚴格遵守），哪些需要高自由度（創意發揮）？
  2. Skill 的單元測試如何做到自動化？你能設計一個 CI/CD pipeline 來在每次 Skill 更新時自動執行測試嗎？
  3. 如果一個 Skill 的 SKILL.md 超過 500 行，你會如何重構？拆成多個 Skills？還是更積極地使用 references/ 目錄？
