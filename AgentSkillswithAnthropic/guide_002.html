核心概念：為什麼需要 Skills？

問題：反覆提示的痛點

本課用一個行銷分析場景來示範痛點。傳統做法是每次對話都要：

  1. 附上 CSV 資料
  2. 描述輸入格式與欄位
  3. 指定品質檢查、漏斗分析、效率指標
  4. 定義輸出格式
  5. 附上預算分配規則文件

這些資訊每次都會被加入 context window，即使後續對話不需要。

關鍵洞察

Context window 是公共財（public good）。每多塞一筆不必要的資料，就增加了 token 消耗、加速 context 填滿、提高回應出錯的可能性。

解法：封裝成 Skill

將上述流程封裝成一個 analyzing-marketing-campaign Skill：

analyzing-marketing-campaign/
├── SKILL.md              # 主要指令（分析流程、指標定義、輸出格式）
└── references/
    └── budget_reallocation_rules.md  # 僅在使用者要求時才載入

SKILL.md 的結構

每個 SKILL.md 都有兩個部分：

  1. YAML Frontmatter：必須包含 name（名稱）和 description（描述）
  2. Markdown 主體：步驟化的指令內容
---
name: analyzing-marketing-campaign
description: Analyze weekly marketing campaign performance data, compute efficiency metrics, and provide budget reallocation recommendations.
---

## Input Requirements
...

## Data Quality Check
...

## Funnel Analysis
...

## Budget Reallocation
When the user asks about budget reallocation, read references/budget_reallocation_rules.md

命名規則

  • 使用小寫字母、數字和連字號（hyphen）
  • 避免使用保留關鍵字（如 Claude、Anthropic）
  • 資料夾名稱必須與 YAML 中的 name 欄位一致

學習路徑

本課的操作流程

  1. 體驗痛點：先用傳統 prompt 方式完成行銷分析（多輪對話）
  2. 建立 Skill：建立 SKILL.md + references 目錄
  3. 打包上傳：將 Skill 資料夾壓縮為 zip，上傳到 Claude.ai Settings > Capabilities > Skills
  4. 實測：在新對話中附上 CSV，Claude 自動偵測並使用 Skill
  5. 結合內建 Skills：用內建的 Excel Skill 產生試算表報告

實務應用

Skill 帶來的三大效益

效益說明
Context 效率預算規則只在使用者要求時才載入，不會佔用不必要的 context
可攜性同一個 Skill 可在 Claude.ai、Claude Code、Codex、Gemini CLI 等環境使用
團隊共享封裝好的 Skill 可分享給團隊成員，確保分析流程一致

結合內建 Skills 的威力

課程展示了自建的行銷分析 Skill 搭配內建的 Excel Skill，自動產生包含以下工作表的試算表：

  • Executive Summary（摘要）
  • Funnel Analysis（漏斗分析）
  • Efficiency Analysis（效率分析）

資安實務應用

想像你建立了一個「弱點評估分析」Skill：定義了 CVSS 評分標準、風險分級規則、報告格式。搭配內建的 Excel Skill，就能自動從掃描結果產生合規報告。每週一鍵完成，不需要反覆描述流程。

常見誤區

誤區：把所有資訊都放進 SKILL.md

像預算分配規則這類「只有部分場景需要」的內容，應該放在 references/ 資料夾，在 SKILL.md 中用條件引用：「When the user asks about X, read references/X.md」。這就是 Progressive Disclosure 的實踐。

誤區：description 寫得太模糊

Description 是模型判斷「何時觸發 Skill」的依據。好的描述會包含具體的觸發情境和關鍵字。例如「Analyze weekly marketing campaign performance from CSV data, compute CTR, CPA, ROAS metrics」比「Marketing analysis」好得多。

延伸思考

Skill 設計 = Prompt Engineering + 軟體工程

設計一個好的 Skill 需要兩種思維的結合：

  • Prompt Engineering：如何清楚地向模型傳達指令、設定期望輸出
  • 軟體工程：模組化、關注點分離、漸進式載入、版本控管

思考題

  1. 你團隊中有哪些「每次都要解釋的 SOP」？它們能分解成哪些 SKILL.md + references？
  2. 如果兩個 Skill 的 description 有重疊，模型可能觸發錯誤的 Skill。你會如何設計 description 來避免這個問題？
  3. Progressive Disclosure 的「條件載入」機制，與你在資安領域見過的哪些設計模式相似？
