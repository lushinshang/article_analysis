核心概念：四者的定位與協作

Skills vs MCP

面向MCPSkills
用途連接外部系統和資料（資料庫、API、服務）教代理如何處理那些資料
提供什麼存取（Access）專業知識（Expertise）
範例MCP Server 連接資料庫Skill 定義「用 A、B 欄位計算指標 X」

精煉比喻

MCP 帶進工具和材料，Skills 告訴你怎麼用它們蓋出東西。

Skills vs Tools

面向ToolsSkills
用途提供代理完成任務的基本能力用專業知識擴展代理的能力
Context工具定義永遠在 context window 中Skills 漸進式載入
彈性固定的能力集合可以包含腳本作為「按需工具」
比喻錘子、鋸子、釘子「如何組裝書架」的說明書

Tools on Demand

Skills 可以包含腳本，這些腳本在需要時才被載入和執行——相當於「按需工具」。如果有些工具不是每次對話都需要，把它們放在 Skill 的 scripts/ 目錄中，比放在全域工具清單中更節省 context。

Skills vs Subagents

面向SubagentsSkills
用途有獨立的 context 和工具權限為主代理或子代理提供專業知識
運作方式主代理分派任務，子代理獨立（可平行）執行告知「工作應該如何完成」
範例Code Reviewer 子代理語言/框架特定的最佳實踐 Skill

Skills 可以同時增強主代理和子代理。主代理可以用 Skill 來決定「如何分派任務」，子代理可以用 Skill 來決定「如何執行任務」。

四者如何協作：Customer Insight Analyzer 範例

組件角色
Skill定義如何分類回饋、如何摘要發現
MCP ServerGoogle Drive MCP，存取客戶訪談記錄和問卷
SubagentsInterview Analyzer（分析訪談）、Survey Analyzer（分析問卷）
Tools底層工具（bash、filesystem）驅動一切運作

AI 生態系的層次架構

Prompts（最基本的原子單位）
  └── Skills（封裝 prompts + 程式碼 + 資源）
        └── Subagents（使用 Skills，獨立 context）
              └── MCP（提供外部資料和工具）
                    └── Tools（底層執行能力）

實務應用

選擇正確組件的決策框架

需求選擇
需要存取外部資料來源MCP Server
需要定義「怎麼做」的知識Skill
需要隔離的 context 或平行執行Subagent
需要底層系統操作（執行、讀寫）Tool
需要可重複、可預測的工作流Skill（可能 + Subagent）
需要跨對話/跨會話持久化Skill（跨對話）+ Subagent（跨會話）

Context Window 保護策略

  • Skills：Progressive Disclosure，只載入需要的部分
  • Subagents：獨立 context，不污染主代理的 context
  • MCP：工具定義載入 context，但資料透過工具呼叫取得

Context Window 最佳實踐

把 context window 想成「共享記憶體」。Skills 用漸進載入保護它，Subagents 用獨立空間保護它，Tool 定義必然佔用它。當你有 100+ Skills 時，Progressive Disclosure 的價值就非常明顯了——只有名稱和描述佔用 context，其餘按需載入。

常見誤區

誤區：用 Skill 取代 MCP Server

Skill 可以包含「查詢資料庫」的指令，但它無法真正連接資料庫。你仍然需要 MCP Server 提供實際的連線能力。Skill 負責「知道怎麼查」，MCP 負責「能夠查」。

誤區：每個任務都用子代理

子代理有額外的資源消耗（token、延遲）。只在需要隔離 context或平行執行時才使用。簡單的順序任務，在主代理中直接處理就好。

延伸思考

持久性（Persistence）的維度

講師提到 Skills 可以跨對話持久化，Subagents 可以跨會話持久化。這意味著：

  • Skills 是「長期知識」——定義了組織如何運作
  • Subagents 是「工作記憶」——記得上次任務的脈絡
  • Prompts 是「即時指令」——只在當下有效

思考題

  1. 在企業環境中，Skills 的管理（建立、版本控管、權限控制）由誰負責？這是 DevOps、知識管理還是 AI 工程的範疇？
  2. 「Tools on Demand」（Skill 中的腳本）和 MCP 提供的工具有什麼根本差異？什麼時候該用前者，什麼時候該用後者？
  3. 如果四個組件的職責邊界模糊（例如 Skill 內嵌了大量腳本，實質上變成了一個「微代理」），你會如何重新設計來保持清晰的關注點分離？
