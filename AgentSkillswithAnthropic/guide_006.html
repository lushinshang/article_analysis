核心概念

Claude Agent SDK 是什麼？

Claude Agent SDK 是程式化建構代理應用程式的框架，使用與 Claude Code 相同的內部架構（harness）。你可以用它來建構自己的 AI 代理應用。

本課建構的研究代理架構

Main Agent (Orchestrator)
├── Skill: learning-a-tool (引導研究方法和輸出格式)
├── MCP Server: Notion (寫入研究結果)
│
├── Subagent: docs_researcher
│   └── Tools: WebSearch, WebFetch
│
├── Subagent: repo_analyzer
│   └── Tools: Bash (git clone), Read, Glob, Grep
│
└── Subagent: web_researcher
    └── Tools: WebSearch, WebFetch

Skill 在 Agent SDK 中的角色

在本課的架構中，Skill 不是給子代理用的——而是給主代理（Orchestrator）用的：

  • 定義研究方法論（Research Methodology）
  • 指定每個子代理應該收集什麼資訊
  • 定義輸出結構（Progressive Learning Levels）
  • 確保工作流的可預測性和一致性

learning-a-tool Skill 的設計

這個 Skill 引導主代理：

  1. 研究階段：分派子代理收集官方文件、GitHub 倉庫、社群資源
  2. 組織階段：將收集的內容組織成漸進式學習層級（載入 references/progressive_learning.md）
  3. 輸出階段：產生 README、resources.md、學習路徑、程式碼範例

Agent SDK 的關鍵配置

Tools（工具權限）

allowed_tools = [
    "Write", "Bash",
    "WebSearch", "WebFetch",
    "Task",                    # 分派子代理
    "Skill",                   # 讀取 Skills
    "mcp_notion_*"             # Notion MCP 所有工具
]

權限規則

子代理使用的所有工具，都必須列在主代理的 allowed_tools 中。即使你在子代理定義中指定了工具，如果主代理沒有允許，子代理也無法使用。

Subagent 定義

agents = {
    "docs_researcher": AgentDefinition(
        description="...",
        prompt=docs_prompt,
        tools=["WebSearch", "WebFetch"]
    ),
    "repo_analyzer": AgentDefinition(
        description="...",
        prompt=repo_prompt,
        tools=["Bash", "Read", "Glob", "Grep"]
    ),
    "web_researcher": AgentDefinition(
        description="...",
        prompt=web_prompt,
        tools=["WebSearch", "WebFetch"]
    )
}

Skills 載入

# Skills 存放在 .claude/skills/ 目錄
# 需要 Skill tool + setting_sources 配置
setting_sources = ["user", "project"]

學習路徑

漸進式建構流程

  1. 基礎骨架：建立最簡單的 Agent（只有 system_prompt + 對話迴圈）
  2. 加入工具：Write、Bash、WebSearch、WebFetch
  3. 加入 MCP：Notion MCP Server + 對應工具權限
  4. 加入子代理：三個研究子代理 + Task tool
  5. 加入 Skills：Skill tool + setting_sources + .claude/skills/ 目錄

實務應用

子代理平行執行

三個子代理同時出發：docs_researcher 找官方文件、repo_analyzer 分析 GitHub 倉庫、web_researcher 搜尋教學和社群資源。這種平行化大幅縮短了研究時間。

Plan Mode

與 Claude Code 類似，你可以要求代理先展示計畫再執行。在本課的範例中：

User: Create a learning guide for MinerU. Show me the plan first.
Agent: [shows research plan + output structure]
User: Proceed.
Agent: [spawns 3 subagents in parallel]

MCP 整合：Notion 寫入

研究完成後，代理讀取 resources.md，轉換為 Notion rich blocks，寫入指定的 Notion 頁面。這展示了 Skills（研究方法）+ MCP（外部系統存取）+ Subagents（平行執行）的完整整合。

資安團隊應用：自動化威脅情報研究

用相同的架構建構威脅情報研究代理：一個子代理搜尋 CVE 資料庫，一個分析相關的 PoC 程式碼，一個收集供應商公告。用 Skill 定義情報分析方法論，用 MCP 寫入 Confluence 或 Notion。

常見誤區

誤區：子代理自動繼承主代理的工具權限

錯。子代理的工具權限需要在兩個地方同時設定：(1) allowed_tools（全域允許清單），(2) AgentDefinition.tools（子代理可用工具）。兩者取交集。

誤區：忽略安全考量

課程中直接允許了 Write 和 Bash 工具而不需使用者確認。在生產環境中，你應該加入人機確認（interrupt）機制，就像 Claude Code 那樣。課程也明確提到這是「待改進」的部分。

誤區：Skills 目錄結構錯誤

在 Agent SDK 中，Skills 必須放在 .claude/skills/ 目錄下，且檔案名稱必須是 SKILL.md（注意大小寫和複數形式）。

延伸思考

Skill 作為 Orchestrator 的引導策略

本課展示了一個有趣的 Skill 使用模式：Skill 不是提供「如何做某件事」的知識，而是提供「如何協調多個代理做研究」的方法論。這開啟了「元 Skill」的設計空間——用 Skill 來定義代理的行為模式，而非具體任務。

思考題

  1. 如果你要為 Skill 加入安全控制（例如限制 Bash 命令的範圍），你會在哪個層級實作？主代理、子代理、還是 Skill 本身？
  2. 子代理平行執行時，如果結果有矛盾（例如兩個來源的資訊不一致），主代理應該如何處理？你會在 Skill 中定義衝突解決策略嗎？
  3. 本課的 learning-a-tool Skill 用 Progressive Disclosure 載入 progressive_learning.md。如果這個參考檔案很大（>100 行），你會如何優化？
